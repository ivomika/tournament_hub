# Экспериментальный AI development workflow

## Назначение

Утверждён 12 октября 2026 года после read-only аудита, опроса и review дизайна. Процесс интегрирован в существующие task-list, карточки, rules и skills. Канонические требования находятся только в [ai-context/workflow.md](../../ai-context/workflow.md); этот документ описывает контекст и проверочный пример, а не второй нормативный процесс.

Task-list сохраняет целочисленные номера и четыре статуса. Этапы, answers/spec/plan, test evidence и approval размещаются в карточке. Для CODE есть human gate перед production; DOCUMENTATION имеет структурные/сценарные проверки. Чистый refactor может использовать baseline GREEN. Skills остаются явно вызываемыми; обычный запрос feature получает workflow через AGENTS/README.

Общий business rule агент может предложить пользователю, но не утверждает сам. В текущей ветке `lib/domain` и бизнес-tests отсутствуют, приложение — минимальный main.dart. Исторические карточки и сохранённый JSON viewer не заменяют действующую бизнес-спецификацию.

## Walkthrough: «Добавить business rule X»

Это гипотетический сценарий в будущем клиенте. Ни новая задача, ни rule X, ни тестовые/production-файлы здесь не создаются. Пользователь определяет условие X, результат Y и ошибки в ходе clarification; они не становятся общими правилами проекта лишь из этого примера.

| Шаг | Что делает агент и где остаются сведения |
| --- | --- |
| 1. Context | Читает AGENTS, ai-context README, router/core, task-list/detail, Flutter rules и workflow. Исследует действующие docs/код/tests; отсутствие источника бизнес-правил обозначает явно. |
| 2. Task | Для новой цели берёт следующий номер из существующего task-list, создаёт detail по template с CODE/DISCOVERY. Для уточнения продолжает прежний номер. Реальный номер в этом walkthrough не резервируется. |
| 3. Questions | Показывает понимание и интерактивно выясняет условие X, результат Y, поведение при ошибке и non-goals; вопросы с готовым ответом в действующих docs не повторяет. |
| 4. Answers/spec | Сохраняет ответы в «Уточнения и решения», дословную историю — в Changelog. Создаёт AC-1/AC-2, границы и сценарии TS-1/TS-2; Stage SPEC_READY. |
| 5. Plan | Пишет plan в карточку: ответственность domain use case, взаимодействия с port, тестовая внешняя зависимость, возможный state-entrypoint, предполагаемые файлы и regression. Показывает краткий plan; Stage PLAN_READY. |
| 6. Test | Создаёт только тест `test/domain/rule_x_test.dart` с реальным ожидаемым бизнес-результатом. Production API/заглушки не создаёт; для внешнего port использует тестовую реализацию. |
| 7. Run | Предполагаемая команда в будущем проекте: из `apps/tournament_app` выполнить `flutter test test/domain/rule_x_test.dart`. Сохраняет cwd/команду, диагностику и версию. Ожидаемое отсутствие нового API может быть compile RED; ошибка SDK/runner — BLOCKED, не RED. Команда в этой документационной задаче не запускалась. |
| 8. Stop | Только после фактического ожидаемого RED ставит RED_CONFIRMED, затем AWAITING_APPROVAL, заканчивает ход кратким отчётом и ждёт. Наличие написанного теста и молчание не разрешают production. |
| 9. Approval | Пользователь отвечает «ок» на этот отчёт. Агент записывает дату, дословный текст, task/контекст, версии spec/plan/test set и evidence в Approval/Changelog. |
| 10. Implement | Теперь возможен production diff в согласованных слоях. Ошибки реализации исправляются до GREEN без нового approval, если spec/test смысл прежний. Assertion не ослабляется ради прохождения. |
| 11. Ambiguity | Если неожиданно нужен новый бизнес-выбор, ставит BLOCKED/🔴 и задаёт вопрос. Если ответ меняет meaning/scope, обновляет spec/plan/tests, подтверждает новое evidence и снова ждёт approval. |
| 12. Done | После успеха test set, выбранной регрессии и mandatory checks выполняет review по критериям/архитектуре/docs/scope. Записывает результаты; Stage DONE и ✅ ставит самостоятельно. |

## Проверка альтернативных путей

| Ситуация | Проверяемый результат |
| --- | --- |
| «Возьми следующую задачу», а запланированных нет | Сообщить факт и уточнить выбор; не создавать цель автоматически. |
| Compile failure из-за отсутствующего API X | Допустим ожидаемый RED без production-заглушки. |
| Compile failure из-за сломанного runner | Не считать RED; блокировать зависимую работу. |
| «Ок» относится к вопросу о формате данных | Записать ответ clarification; approval реализации отсутствует. |
| Сессия возобновлена в AWAITING_APPROVAL | Прочитать карточку/evidence и ждать; прежний 🚧 не даёт разрешения. |
| Чистый рефакторинг без смены поведения | Подтверждённый baseline GREEN и human gate сохраняются. |
| Новый test GREEN сразу | Проверить существующее поведение/необходимость diff; не портить тест искусственно. |
| Ошибка реализации после approval | Исправить в утверждённом scope, повторить tests; новая business ambiguity отличается от technical bug. |
| Намеренная смена смысла AC/test | Сначала новая spec/test/evidence и gate; прежний approval не переносится. |
| Refactor ломает regression | Вернуть GREEN, не менять ожидаемый бизнес-результат. |
| Вызван task skill | Подготовить постановку, оставить planning-only; ни тестов, ни implementation. |
| Documentation-only request | Структурные/сценарные checks, без искусственного RED. |
| Required GREEN проверить нельзя | Не объявлять code task DONE; явно указать blocker. |

Проверка здесь — документированный walkthrough и review переходов, а не исполнение product feature. Автоматической tool-блокировки нет: корректность gate зависит от чтения instructions и честного audit evidence. Этот предел не скрывается утверждением, что существуют заголовки template.
