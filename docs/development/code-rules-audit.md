# Аудит кода по правилам проекта

## Вызов

Репозиторный skill находится в [.agents/skills/code-rules-audit/SKILL.md](../../.agents/skills/code-rules-audit/SKILL.md). Он предназначен для явного вызова пользователем; implicit invocation отключён. В окружении, где skill ещё не появился в списке, его можно вызвать ссылкой на этот файл.

Примеры запросов:

- `$code-rules-audit` — проверить текущий diff.
- `$code-rules-audit проверь весь код` — проверить исходники проекта целиком.
- `$code-rules-audit проверь задачу 27` — определить scope по записи task-list и карточке задачи.
- `$code-rules-audit проверь diff относительно <ref>` — использовать явно выбранную базу сравнения.

## Scope и достоверность

По умолчанию проверяются unstaged, staged и новые untracked-файлы относительно HEAD. Контекст вокруг изменения читается для обоснования findings; существующее нарушение вне diff отделяется от внесённого изменения. Если diff пуст, аудит не подменяется проверкой всего проекта.

В режиме всего кода проверяются исходники приложения, инструменты, тесты и конфигурация. Зависимости и build/cache не входят в scope. Generated-код рассматривается вместе с источником генерации; исправление должно направляться в source/generator.

Scope задачи определяется по записанным paths/refs/коммитам. Когда известны только paths, проверяются актуальные файлы целиком и это явно указывается в отчёте. Номер задачи и её описание не доказывают принадлежность всех грязных файлов этой задаче. Если подтверждённого scope недостаточно, отчёт показывает проверенную часть и недостающие сведения.

## Процесс и результат

Findings используют текущие leaf ID (`R-003.d`, `R-006.b`). [Организация правил](rule-organization.md) разделяет общий core scope и Flutter scope; архитектуру R-003 нельзя переносить на JS/spectator. Для review изменений правил проверяются размещение, регистрация и документирование по `maintenance.md`.

При каждом вызове агент заново читает router, обязательные и применимые conditional rules и связанные архитектурные документы. Он сначала проверяет согласованность и проверяемость правил, затем код выбранного scope. Для каждого правила в отчёте указывается результат или причина неприменимости/неполной проверки.

Finding содержит идентификатор правила, путь и строку, фактическое нарушение, последствия и направление исправления. Результаты поиска текста требуют проверки по коду: `build` и реальные builders не считаются Widget helpers, а разрешённый builder callback не считается нарушением запрета лямбд.

Аудит не исправляет код и правила автоматически, не создаёт задачи и не коммитит. Исправления выполняются по отдельному запросу пользователя в рамках процесса task-list. Это проверка агентом с опорой на факты, а не автоматический lint: отсутствие findings ограничено фактически прочитанным scope. В этой задаче создан workflow проверки, но полный аудит приложения не проводился.
