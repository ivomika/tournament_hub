# Границы слоёв приложения

## Решение

Принято 4 октября 2026 года. Архитектура Flutter-клиента разделена на четыре слоя внутри `apps/tournament_app/lib`: `app`, `domain`, `infrastructure`, `presentation`. Это целевая архитектура разработки; документ не является подтверждением соответствия всего существующего кода. Папки создаются при появлении реализации, а не заранее.

## Ответственность слоёв

| Слой | Что содержит | За что отвечает |
| --- | --- | --- |
| `app` | Bootstrap, routing, DI и сборка приложения | Инициализирует инфраструктуру, связывает реализации с domain ports, создаёт use cases и state/controllers, передаёт зависимости экранам |
| `domain` | Entities/models, use cases, ports | Хранит бизнес-правила и сценарии приложения; определяет необходимые контракты без деталей UI, хранения и транспорта |
| `infrastructure` | Реализации domain ports, технические core-абстракции и адаптеры | Выполняет операции хранения, HTTP и другие платформенные механизмы через заменяемые реализации |
| `presentation` | Widgets, экраны, UI-state и controllers | Отображает данные, принимает действия пользователя, управляет состояниями загрузки, результата и ошибки; вызывает сценарии через state |

`main.dart` — входная точка: передаёт запуск bootstrap из `app`. В нём не размещаются бизнес-сценарии и реализации портов.

## Направление зависимостей

Таблица описывает импорты между слоями. Зависимости внутри собственного слоя разрешены.

| Кто импортирует | `app` | `domain` | `infrastructure` | `presentation` |
| --- | --- | --- | --- | --- |
| `app` | — | Да | Да | Да |
| `domain` | Нет | — | Нет | Нет |
| `infrastructure` | Нет | Да | — | Нет |
| `presentation` | Нет | Да | Нет | — |

Запреты распространяются и на косвенное раскрытие чужого слоя: re-export, публичные типы, service locator и глобальные контейнеры. Например, presentation нельзя получать infrastructure-клиент из DI-контейнера даже без прямого импорта файла реализации.

`app` — единственное место связывания domain и infrastructure для DI. Infrastructure-класс реализует domain port, а выбор реализации и её передача use case выполняются в `app`. Routing в `app` создаёт presentation с готовыми зависимостями. Для навигации presentation получает callback или подходящий контракт без обращения к `app`.

## Путь действия пользователя

```text
Widget → state/controller → domain use case → domain port
                                               ↑ реализует
                                      infrastructure adapter
```

Стрелка к port обозначает вызов контракта, а не импорт infrastructure из domain. Конкретную реализацию передаёт `app` при сборке.

Widgets отправляют действия в state/controller и отображают его состояние. Только state/controller в presentation вызывает use cases. Widget не хранит use case, не получает его через provider/service locator и не вызывает его ни в callback, ни в lifecycle-методе. State/controller не вызывает domain ports напрямую и не реализует бизнес-правила.

State/controller может управлять UI: загрузкой, доступностью кнопок, выбранной вкладкой, сообщением об ошибке и преобразованием результата в состояние экрана. Расчёт очков, проверка допустимости результата матча, выбор чемпиона и порядок бизнес-операций принадлежат domain. Use case может вызывать другие domain-объекты и сценарии: ограничение «только state» определяет вход из presentation в use cases.

Bootstrap собирает зависимости и запускает приложение. Если экрану нужен начальный бизнес-сценарий, его вызывает state/controller; routing и bootstrap не обходят эту точку входа.

## Ports и технические абстракции

Контракт, необходимый бизнес-сценарию, определяется в `domain`: например, сохранение турнира через repository/port. Контракт использует domain-модели и обычные Dart-типы; в него не попадают объекты SDK, HTTP response, SQL connection или Flutter context.

Технические core-абстракции находятся внутри `infrastructure`. Например, собственный `HttpClient` или контракт соединения с БД скрывает используемую библиотеку от инфраструктурных механизмов, которые его потребляют. Адаптер конкретной библиотеки реализует эту абстракцию. Предметный repository может использовать такой технический клиент при реализации domain port.

Для каждой реально используемой технической механики задаётся минимальный собственный контракт, достаточный её потребителям. Не требуется копировать весь API библиотеки или создавать обёртку вокруг каждого её класса. Выбор конкретного адаптера и его wiring выполняются в `app`; библиотечные типы остаются внутри адаптера.

## Зависимости domain от пакетов

Domain использует Dart и не зависит от Flutter, UI, платформенных SDK, библиотек хранения, HTTP или других слоёв приложения. Возможен минимальный явно утверждённый набор технических пакетов, которые не привязывают domain к этим механизмам.

Runtime-пакеты и генераторы различаются: например, `Equatable` — runtime-зависимость, а не генератор. Он может быть кандидатом для такого набора, но упоминание здесь не добавляет пакет в проект и не разрешает произвольные зависимости. Добавление пакета требует документированного решения: цель, используемый API, влияние на независимость domain и необходимость генератора/runtime-части. Решение сопровождает изменение зависимостей в той же задаче.

## Последствия и проверка изменений

- Presentation можно создавать и проверять с подменёнными use cases без доступа к инфраструктуре.
- Реализацию port и технического адаптера можно заменить, сохранив domain-контракт.
- Изменение бизнес-правил выполняется в domain; изменение отображения — в presentation; wiring — в app.
- При review проверяются импорты, публичные типы, место вызова use cases и отсутствие бизнес-правил в state/widgets.
- Изменение этих границ оформляется отдельным архитектурным решением с обновлением этого документа и связанных правил. Автоматический checker для всех перечисленных ограничений этим решением не вводится.
