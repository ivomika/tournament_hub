# Отменяемые асинхронные операции

Решение2026-11-10: проектные асинхронные операции должны поддерживать отмену. Требование действует на семантику операции, включая возвращающие Future функции без async, подписки, таймеры и detached задачи. Исполнение закреплено [R-009](../../ai-context/rules/core/009-cancellable-async.md).

## Контракт и владелец

У каждой операции есть владелец: запрос, interaction, presentation controller или application session. Владелец управляет временем жизни и отменой. Публичный контракт предоставляет отмену через token/scope либо operation handle; вложенные helpers могут использовать тот же контекст отмены и не создают собственный независимый lifecycle для каждого await.

Отмена — отдельный типизированный исход. Отказ guard, техническая ошибка и пользовательское закрытие различаются. Запрос отмены идемпотентен. Все проектные ожидания получают завершение, а поздние callbacks не меняют завершённый исход. Проверки bool/enum сами по себе не отменяют работу.

Не ожидающая результата функция также имеет владельца и обработку ошибок. unawaited не заменяет владение или отмену. Подписки и таймеры освобождаются фактическими cancel; listener снимается с источника. Cleanup при отмене обязан закончиться и освободить ресурсы; требование отменяемости не применяется к самому завершению cleanup рекурсивно.

## Границы отмены

Обычный Dart Future — уведомление о завершении, а не механизм принудительной остановки. Отмена обёртки не доказывает остановку HTTP, записи в БД или уже выполненного push. Адаптер передаёт отмену внешнему API, когда он её поддерживает; если физическая остановка невозможна, прекращает проектное ожидание и доставку результата, документирует продолжающуюся работу и её побочные эффекты. Уже зафиксированная запись не объявляется откатанной.

Для необратимого шага описывается точка фиксации: до неё отмена предотвращает действие, после неё учитывается реальный выполненный результат. Нельзя сообщить «отменено, ничего не произошло», если побочный эффект уже состоялся. Cancellation token не гарантирует rollback.

NavigationCoordinator переведён на общий scope в задаче109. Это не доказывает соответствие всего существующего async-кода: новый и изменяемый контракт проверяется отдельно; затронутый старый дефект фиксируется явно, а не скрывается blanket exception.

## Scope операций владельца

Решение2026-11-11: вместо ручных lifecycle-проверок в каждом рабочем методе использовать общий scope владельца. В задаче109 реализован OperationScope для presentation controller и app. Это собственный контракт проекта, а не универсальная рекомендация команды Flutter или автоматическая возможность Dart Future.

Scope регистрирует каждую операцию до вызова ленивой request factory. После завершения снимает её с учёта. Один close закрывает доставку всех pending результатов, запрещает новые запуски, передаёт отмену источникам и ждёт cleanup всех, включая ранее отменённые, но ещё очищающиеся операции. Ошибки cleanup собираются и доступны вызывающему; одна ошибка не останавливает очистку других ресурсов. Индивидуальный handle позволяет отменить одну операцию, сохранив остальных.

Наблюдаемые исходы различают значение, ошибку и отмену с причиной requested/ownerEnded/scopeClosed. Проектное ожидание отмены завершается до конца cleanup; cleanup имеет отдельное ожидание cancel/close. Повторные cancel/close возвращают то же ожидание, источник не отменяется повторно. После закрытия request factory и UI callbacks не вызываются. Поздние ошибки внешнего Future наблюдаются, но не доставляются завершённому владельцу.

Доставка в state синхронная. После начала callback scope не может прервать его выполнение; закрытие из самого callback сохраняет уже начатую доставку. Исключение callback становится ошибкой операции без рекурсивного вызова того же обработчика. Новая асинхронная работа внутри обработчика должна отдельно наследовать владельца.

Реализация находится в [presentation/operations](../../apps/tournament_app/lib/presentation/operations/operation_scope.dart), использует только dart:async, без пакетов и Flutter API. App вправе использовать presentation-контракт; domain/infrastructure не получают обратного импорта. Общая утилита lifetime не становится бизнес-сущностью. Перенос контракта на другие слои требует отдельного определения нужного им ownership, без обхода матрицы импортов.

### Использование

Владелец создаёт отдельный OperationScope для своей работы; не использует общий singleton scope нескольких экранов. Рабочий метод регистрирует источник и callbacks:

```dart
final operation = operations.run<Profile>(
  request: startProfileRequest,
  onResult: showProfile,
  onError: showProfileError,
);
```

Здесь startProfileRequest — именованный метод controller/app-адаптера с результатом OperationRequest<Profile>. Он создаёт реальный запрос и передаёт его Future и настоящий onCancel. Вызовы business use cases остаются в state/controller; scope не получает domain ports или DI. Пустой onCancel не выдаётся за остановку внешней работы.

Когда нужен отдельный результат, operation.result возвращает OperationOutcome<Profile>; когда нужна отдельная отмена, await operation.cancel() ждёт её очистки. Отмена не вызывает onResult/onError: она доступна как OperationCancelled в result. При завершении владельца достаточно await operations.close(); обычные рабочие методы проверок isDisposed не содержат. Ошибки cleanup поступают из cancel как исходная ошибка, из close как OperationCleanupException с неизменяемым errors. Если индивидуальная очистка завершилась сбоем, следующий общий close тоже сообщает его, не вызывает источник повторно.

Контракт onResult/onError требует синхронного callback. Dart void callback сам по себе не запрещает передать async-функцию; это ограничение проверяется review. Асинхронный callback доставки не поддерживается: его продолжение не управляется scope. Такую работу следует регистрировать отдельной операцией с собственным handle отмены.

Scope хранит авторитетное состояние операции и своего закрытия; отдельный дублирующий isDisposed не нужен. Это не означает отсутствия lifecycle-состояния внутри механизма. Owner по-прежнему обязан закрыть scope. Если Flutter dispose синхронен, owner-обвязка должна сразу инициировать закрытие и явно наблюдать Future очистки и его ошибки; unawaited без обработки ошибок не является завершением shutdown.

Продуктовые bindings, DI и универсальный binding Flutter lifecycle не создавались в этом срезе. Контракт проверен18 сценариями [operation_scope_test.dart](../../apps/tournament_app/test/presentation/operations/operation_scope_test.dart), включая10 одновременных операций и reentrant close.

### Миграция существующей навигации

NavigationCoordinator использует один OperationScope владельца. Вход submit регистрируется до чтения контекста и постановки в очередь; непосредственно перед извлечённым из очереди выполнением тот же scope регистрирует исполнение. Это две фазы одного navigation request, а не отдельный scope на каждый вызов. Вторая граница нужна, чтобы закрытая очередь вообще не запускала guard/readContext/executor. Повторные intent по-прежнему разделяют одно in-flight выполнение, а origin/revision и FIFO сохраняются.

dispose синхронно инициирует operations.close и очищает pending registry. Общее закрытие сразу завершает ожидания активных, queued и coalesced запросов как NavigationCancelled. Cleanup Future наблюдается; неожиданный сбой передаётся Zone error handler. AppNavigationSession продолжает вызывать coordinator.dispose перед освобождением router. После dispose submit не читает контекст router, late success/error от execute не меняет исход и не доставляется вторично.

NavigationEffectExecutor.execute по текущему контракту возвращает обычный Future без физического cancel. Поэтому coordinator освобождает проектные ожидания; уже начатое SDK-действие может продолжаться. Его поздний результат наблюдается scope; выполненные push/go/pop не откатываются. Cleanup этого источника не выдаётся за физическую остановку executor. Закрытая очередь после отмены активного проектного ожидания доходит до своих записей и отвергает их до запуска factory, даже если исходный execute ещё не завершился. Доступ к SDK после dispose не добавляется: существующий executor после frame await только возвращает исход и снимает activeEffect.

Четыре regression scenarios настоящего coordinator подтверждают немедленное завершение активного/queued запроса, запрет контекстного чтения после dispose, подавление late error и повторный dispose с дубликатами. Полный выбранный набор:95 PASS (18 scope +77 navigation). Сохранённых bool lifecycle flags в Dart runtime apps/tools по целевому scan не осталось; это не универсальное AST-доказательство ownership.

## Что проверять

Проверки выбираются по поведению: отмена до старта не запускает side effect; отмена во время ожидания завершает проектное ожидание; повторная отмена безопасна; поздний результат не доставляется повторно; ресурсы освобождены; успешный исход, ошибка и отмена сохраняют смысл при гонке. Для необратимых операций отдельно проверяется граница commit.

Автоматического AST-доказательства отменяемости нет. Наличие параметра token не доказывает его использования. Требование проверяется review контрактов и поведенческими тестами; node tools/check_rules.cjs проверяет только согласованность реестра правил.

## Основания

- [Flutter State.setState](https://api.flutter.dev/flutter/widgets/State/setState.html) рекомендует отменять работу вместо одной проверки mounted.
- [StreamSubscription.cancel](https://api.dart.dev/dart-async/StreamSubscription/cancel.html) прекращает доставку событий и возвращает завершение очистки.
- [CancelableOperation](https://pub.dev/documentation/async/latest/async/CancelableOperation-class.html) отделяет отменяемую операцию от Future. Его value после отмены не завершается; проектный контракт обязан выбрать завершающийся cancellation outcome, например через valueOrCancellation внутри адаптера. Это исследованный вариант, не выбор зависимости проекта.
