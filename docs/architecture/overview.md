# Обзор архитектуры

Tournament HUB — local-first система с двумя пользовательскими приложениями:

```text
Flutter Host (авторитетное состояние + локальный сервер)
                         |
                    локальная сеть
                  /                 \
Flutter Participant              React Spectator
полное производное состояние     display projection только для чтения
```

Host владеет активным состоянием `LocalGroup` и `Tournament`. Состояние Participant и Spectator можно восстановить: при подключении или reconnect они сходятся с Host через полный snapshot, после чего применяют инкрементальные event в порядке revision.

## Категории состояния

- Постоянное личное состояние: identity, профиль, история и настройки; карьера и достижения вычисляются из истории.
- Постоянное состояние Host: данные активного турнира, сохраняемые достаточно часто, чтобы перезапуск приложения не приводил к потере введённых результатов.
- Состояние сессии: соединения, ожидающие подтверждения заявки, spectators и временное состояние transport.
- Производное состояние: таблица, карьера, достижения и spectator display projection.

## Локальный профиль

Для MVP устройство хранит один локальный профиль. Его стабильная identity не зависит от изменяемого nickname. Domain-модель и repository contract находятся в profile feature и не зависят от Flutter или технологии хранения. Отсутствие профиля является нормальным состоянием первого запуска, а ошибки чтения и записи представлены отдельно.

## Локальный tournament draft

Первый Tournament Core создаёт draft из ровно одного обязательного `LocalProfile` и одного или нескольких `GuestProfile`. Гостевой профиль является временной отдельной сущностью и не превращается в постоянный профиль устройства.

`TournamentParticipant` хранит snapshot identity, nickname и source на момент создания. Последующее переименование исходного профиля не меняет уже созданный состав. Domain проверяет минимум двух участников, единственность local profile и отсутствие duplicate identity. Application use case получает ID и persistence через ports; Flutter, Drift, assets и сеть остаются за границей Core.

## Подготовка турнира

Application-сценарий подготовки получает сохранённый draft и координирует две независимые domain-политики. `TournamentRules` создаёт расписание, а `FighterAssignmentStrategy` распределяет бойцов из `FighterRegistry`. Результат объединяется в `TournamentSetup`, который повторно проверяет полноту состава и уникальность назначений.

Текущая реализация правил создаёт один детерминированный круг round robin. Текущая стратегия бойцов выбирает уникальные значения случайно через `RandomIndexGenerator`; production-адаптер случайности находится вне domain. Благодаря этим границам формат турнира, способ назначения и источник случайности заменяются независимо.

Double Elimination подключается через обобщённую `TournamentFormatStrategy`. Его topology, продвижение, grand-final reset, placement replay и пересчёт после исправлений находятся в domain. Источник случайности остаётся port: production использует системную случайность, tests — воспроизводимую реализацию. Координаты и способ отображения bracket не входят в domain state.

## Основной поток данных

```text
действие UI -> application command -> domain validation -> изменение агрегата
           -> локальное сохранение -> event/projection с revision -> клиенты
```

При завершении Host создаёт неизменяемый и самодостаточный Tournament Snapshot и повторяет его доставку каждому Participant до подтверждения. Стабильный идентификатор турнира делает импорт snapshot идемпотентным.

Production bundle React собирается отдельно и встраивается во Flutter-приложение. Локальный сервер Host раздаёт его браузерам в той же сети.

## Spectator Host

Flutter запускает `dart:io` HTTP/WebSocket-сервер на всех IPv4-интерфейсах устройства. HTTP раздаёт встроенный production bundle React и fighter assets, а endpoint `/ws` передаёт versioned full snapshot. Host показывает фактический LAN URL, QR-код, действие копирования и число подключённых клиентов. Если стандартный порт занят, transport выбирает свободный порт без изменения application/domain слоёв.

`SpectatorPublisher` является application port. Контроллеры обоих форматов публикуют snapshot только после успешного локального сохранения, включая authoritative `finished` snapshot. `SpectatorSnapshotMapper` формирует display projection; React не рассчитывает турнирное продвижение и не изменяет состояние Host.

Клиент подключается к `/ws` того же origin, принимает только совместимую версию протокола, применяет монотонно возрастающие revisions и запрашивает полный snapshot при reconnect. Последний snapshot хранится на сервере и немедленно отправляется новому клиенту, поэтому подключение к уже завершённому турниру сразу открывает финальный экран. Контракт и примеры сообщений описаны в `docs/protocol/README.md`.

## Presentation и размеры экрана

Архитектура presentation следует принципу mobile-first, но не связывает пользовательский сценарий с фиксированным размером телефона. Domain и application слои одинаковы для всех платформ, а Flutter presentation выбирает композицию по доступной ширине и возможностям ввода.

Desktop-представление является адаптацией, а не масштабированием мобильного дерева widgets. На широком экране presentation может менять навигацию, ограничивать ширину основного контента, показывать связанные области рядом и использовать master-detail. Изменение размера окна должно приводить к предсказуемой перестройке без потери состояния или доступных действий.

Подробные требования и критерии проверки описаны в `docs/product/platform-and-responsive-ui.md`.
