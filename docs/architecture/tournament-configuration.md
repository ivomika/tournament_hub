# Создание и настройки турнира

Задача115, 2026-11-13. Статус: проектирование, runtime ещё не реализован. Ниже разделены подтверждённые продуктовые решения и предлагаемый контракт реализации. Начало CODE потребует отдельного test-first gate; наличие этого документа не подтверждает работу создания в приложении.

## Граница этапа

Результат этапа — локально сохранённый **незапущенный турнир** с названием и настройками. В коде его удобно представлять как TournamentDraft: создание не равнозначно старту соревнования. Состав/участники, подключения/QR/server, spectator, персонажи/раздача, матчи/сетка/раунды/очки и запуск не входят. Кнопка «Создать» не должна запускать эти механизмы или вести в их незавершённые экраны.

Существующая реализация содержит TournamentId, SetupScreen и визуальные DE/SE/RR fixtures. Полноценной domain-модели настроек, persistent repository, controller/binding и действующего Home→Setup flow пока нет. Документ не опирается на удалённые старые design docs: действующий источник правил — [MK11](../source/mk11_tournament_rules_ru.md).

## Подтверждено пользователем

- Одновременно хранится **один настраиваемый турнир**. Новый Create не заменяет существующую запись молча. Это не решение о количестве любых будущих запущенных/завершённых турниров.
- Сохранение **явное**, по «Создать»/«Сохранить», после подтверждения записи — возврат на главную с карточкой турнира. Автосохранения нет.
- FT для DE/SE — **любое целое от1 без продуктового верхнего ограничения**. Max3/max5/max9 не вводятся. Техническое представление/codec/stepper не должны молча терять точность, обрезать значение или переполняться.
- Выход из изменённой формы требует подтверждения потери несохранённых изменений. Сам выход не записывает данные.

## Настройки по source

| Параметр | DE | SE | RR |
| --- | --- | --- | --- |
| Основной FT | FT1 по умолчанию, настраивается | FT1 по умолчанию, настраивается | Всегда FT2, не настраивается |
| FT финала | Grand Final наследует основной или имеет явное переопределение | Финал наследует основной или имеет явное переопределение | Отдельного финального FT нет |
| Bracket Reset | Всегда; использует FT Grand Final | Не применяется | Не применяется |

DE — основной формат по умолчанию; SE/RR доступны. Настройки очков/tie-break/Bye не выводятся как произвольные переключатели: их смысл задан source, но исполнение относится к будущему проведению турнира. Минимум2 игрока проверяется при будущем старте; незапущенный configuration draft можно создать без участников.

Наследование финального FT — отдельное намерение: изменение основного FT меняет наследуемый финальный FT. Явный override остаётся отдельным даже при совпадении чисел с основным. Нельзя сохранить только effective число и потерять это различие. Reset DE не получает выключатель или отдельный FT.

## Предлагаемый пользовательский flow

```text
Главная без турнира
  → «Создать турнир»
  → форма: название + DE/SE/RR + применимые FT
  → «Создать»
  → подтверждённая запись
  → главная: карточка «Не запущен» / «Настроить»
  → редактирование того же турнира
  → «Сохранить»
  → главная с обновлённой карточкой
```

Карточка незапущенного турнира не маскируется под текущий матч или активную сетку. На ней не нужны фиктивные участники, счёт, QR, кнопка Start и пустая статистика. Конкретные подписи/компоновка — предложение UI, которое проверяется при реализации на mobile/desktop.

Предлагается непустое название после trim; в source отдельной валидации названия нет, поэтому это часть plan1, а не новое утверждённое общее business rule. Новая форма не сохраняет запись при открытии/каждом вводе. У существующего турнира поля загружаются из repository; ID при сохранении остаётся тем же.

Для финала предлагается явный выбор «Как в основной сетке»/«Отдельный FT». Контрол FT финала доступен для отдельного значения; возвращение к наследованию снимает override. RR показывает FT2 как неизменяемый факт и не содержит настраиваемого FT. При переключении формата название остаётся; общие DE/SE значения можно удерживать в рабочем буфере формы, но не сохранять неактуальные elimination-поля внутри RR.

Чистый Back уходит без лишнего вопроса. Для изменённой формы подтверждение предлагает остаться или выйти без сохранения; dismiss/Back самого modal оставляет форму. В режиме редактирования discard сохраняет прежнюю запись, в создании — не создаёт новую. Во время save конкурирующий выход блокируется; lifecycle close прекращает доставку результата, не обещая rollback уже начатого источника.

## Предлагаемый domain и границы

- **TournamentDraft** — минимальные immutable данные ID/названия/настроек и фиксированная ссылка на применяемый ruleset. Ни participants, ни empty matches/results коллекции не добавляются заранее.
- **Настройки/FirstTo** — типизированные значения. Общая конфигурация FT для DE/SE; отдельный вариант RR без изменяемого FT. Изменение формата не разрешает незаконную комбинацию параметров.
- **Правила конфигурации** — небольшой domain-интерфейс defaults/validation с реализацией по MK11. Это точка замены правил, а не реализация всего турнирного engine. UI не выбирает/не изменяет ruleset; текущий ruleset-reference существующего draft сохраняется. Неизвестная persisted версия даёт typed failure без тихой подмены актуальными правилами.
- **Repository** — один authoritative persistent источник сохранённого draft, минимальные read/create/update операции. Create проверяет занятый слот и не затирает данные; update проверяет ID и сохраняет его. App snapshots/presentation projections не становятся второй базой.
- **Use cases** — load/create/update. Новый TournamentId формируется через существующий общий IdentifierGenerator/UUID adapter; генерация не происходит в widget или обычном preview.
- **Infrastructure** — codec и adapter хранилища, без раскрытия библиотечных типов. Конкретный backend выбирается по гарантиям create-conflict/concurrency/idempotency. Сам факт наличия SharedPreferencesAsync не доказывает атомарность compare-and-create или crash-durability. Эту гарантию нельзя заменить only double-click guard в controller.
- **Presentation/app** — controller вызывает use cases; app связывает зависимости и typed routing. SetupScreen получает state/callbacks, использует DS и runtime themes. Подтверждение выхода открывает общий modal adapter через intent/guard/effect, не прямой showDialog из screen.

Повтор/cancel после неопределённого save не должен создавать второй ID или затирать чужую запись. Чтение после перезапуска восстанавливает фактически сохранённый слот. Повреждённые/неподдерживаемые данные отличаются от отсутствия записи; приложение не удаляет их и не создаёт новый турнир автоматически.

Точные имена классов и сигнатуры уточняются в executable tests будущего CODE, без переименования существующего TournamentId ради нового слоя абстракций. Новые зависимости и широкая универсальная ORM/CRUD/framework не утверждаются этим планом.

## Проверки будущей реализации

- Реальные settings/policy/use cases: defaults, positive FT, большие значения, inheritance/override, fixed RR, неизменяемые ID/ruleset, create conflict и restart recovery.
- Реальные controller/router: Create→Home→Edit→Home, double submit/конкурирующий create, stale origin, dirty confirmation stay/discard/dismiss, ошибки read/write, отмена/late completion и отсутствие ложного success.
- Только внешние storage/clock/ID/output dependencies заменяются fakes; проверяемая бизнес-логика не подменяется.
- R-010: scoped typed events и конкретные фазы/причины/последствия, correlation/retry и безопасный error/stack, без dump названия/payload.
- Widgetbook и native goldens: DE/SE/RR, наследуемый/отдельный финал, create/edit/loading/invalid/saving/error/confirmation и карточка главной. Новый визуальный элемент создаётся в DS с темой/golden по мере необходимости, без пустых папок заранее.
