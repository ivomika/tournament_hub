# Композиция widgets и callbacks

## Решение

Принято 11 октября 2026 года. Фрагменты UI оформляются приватными widgets с явными параметрами. Обработчики действий передаются именованными методами; анонимные функции разрешены только для builder-контрактов. Решение дополняет [границы слоёв](layer-boundaries.md) и [типизацию, локализацию и темы](typed-localized-themed-ui.md).

## Извлечение фрагмента UI

Метод вроде `Widget _buildParticipant(...)` превращается в приватный widget, например `_ParticipantSummary`. Его конструктор получает конкретную модель, тему и нужные callbacks. Это делает зависимости фрагмента видимыми и позволяет Flutter работать с отдельным элементом дерева.

Нельзя обходить ограничение через getter, локальную функцию или функцию, возвращающую подтип Widget. Обычный framework `build` остаётся точкой композиции. Builder API, например `ListView.builder`, также может возвращать Widget: его назначение подтверждено контрактом framework. Helper не становится builder лишь потому, что называется `_build...`.

У приватного widget по возможности есть `const`-конструктор; создание через `const` используется при константных аргументах. Динамические модели, state и тема не требуют искусственных констант. Приватный widget продолжает получать визуальные значения из темы своего компонента.

## Обработчики

Вместо `onPressed: () => state.submit()` widget содержит именованный метод `_handleSubmit`, который обращается к state/controller; в callback передаётся `_handleSubmit`. Для callbacks с аргументами метод имеет соответствующую типизированную сигнатуру.

Когда действие связано с конкретной моделью, приватный widget хранит эту модель в типизированном поле и передаёт её из именованного обработчика. Анонимная обёртка для привязки аргумента не используется. Если widget принимает уже именованный callback, его можно передать дальше напрямую.

Доступность действия сохраняется при передаче обработчика. Если UI API принимает nullable callback, недоступное действие получает `null`: например, `onTap: state.canSubmit ? _handleSubmit : null`. Пустой обработчик, в том числе именованный, оставляет callback установленным и не выражает отсутствие действия. Проверка доступности только внутри обработчика также не заменяет `null`. State/controller определяет доступность, а widget передаёт соответствующее значение. Для API без nullable callback способ отключения определяется его контрактом; это уточнение не требует менять такой API.

Builder может быть анонимным, когда контракт потребителя предназначен для построения UI. Асинхронность, расположение в lifecycle, callback таймера, `map`/`where` внутри widget или похожее имя функции сами по себе не дают исключения. Именованные обработчики не переносят бизнес-логику в widgets и не обходят state при вызове use cases.

## Проверка

Проверяются функции, возвращающие widgets, и все анонимные функции внутри widgets. Для каждого исключения устанавливается реальный framework/builder-контракт. Документ задаёт требования для разработки; существующий код не был автоматически мигрирован или признан соответствующим им. Аудит выполняется по [руководству проверки правил](../development/code-rules-audit.md).
