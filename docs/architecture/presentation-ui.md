# Архитектура визуального слоя

## Решение и границы

Принято 12 октября 2026 года по интерактивному согласованию задачи 33. Весь проектный UI располагается в `apps/tournament_app/lib/presentation`. `app` создаёт зависимости и запускает оболочки, но не определяет widgets, оформление или экранные композиции. Domain/infrastructure не содержат UI.

Это развитие [границ слоёв](layer-boundaries.md) и [токенизированных тем](typed-localized-themed-ui.md). Визуальная часть не требует логического TestGate; обязательная golden-проверка — отдельный процесс, описанный в [визуальном workflow](../development/visual-workflow.md).

## Структура

```text
presentation/
  design_system/
    foundation/
      <foundation_scope>/
    components/
      <component>/
        <component>.dart
        <component>_theme.dart
        golden/
    widgets/
      <composition>/
        <composition>.dart
        <composition>_theme.dart
        golden/
  screens/
    <screen>/
      <screen>.dart
      <screen>_theme.dart
      <screen>_presentation_contract.dart
      golden/
  widgetbook/
    foundation/<scope>/<use_case>/
    components/<component>/<use_case>/
    widgets/<composition>/<use_case>/
    screens/<screen>/<use_case>/

test/presentation/
  design_system/components/<component>/
  design_system/widgets/<composition>/
  screens/<screen>/
```

Имена в угловых скобках — шаблоны, не реальные папки. Папку конкретного элемента создают только при его реализации; пустые папки будущих кнопок/экранов не резервируют. Запрошенные верхнеуровневые scopes могут содержать короткий указатель на этот документ.

### Foundation

Базовые принципы: семантические цвета, typography, spacing, размеры, shape, borders, shadows, opacity, иконки, motion, breakpoints. Каждый реализованный scope имеет отдельную папку. Общая типизированная тема собирается из foundation; темы компонентов используют её токены. Палитра, шрифты и числовые значения утверждаются вместе с реальным дизайном, не выдумываются ради каркаса.

Токен, value object или тема сами по себе не являются визуальным widget и не требуют собственного PNG. Визуальный компонент foundation (например, самостоятельный типографический примитив) требует golden на общих основаниях.

### Components и widgets

`components` — небольшие самостоятельные элементы с явным контрактом, вариантами и собственной темой. `widgets` — переиспользуемые композиции foundation/components/widgets. Направление композиции не превращает DS в копию экранов: DS не импортирует screens, Widgetbook, продуктовые controllers, DI или use cases.

Повторяющийся блок извлекается в DS-композицию и используется экранами, а не рисуется повторно. Извлечение требуется при подтверждённом повторном использовании; произвольные универсальные фабрики «на все будущие экраны» не создаются.

В каждой папке элемента его widget, типизированная тема и `golden/`. Предметные параметры и callbacks не являются темой. Оформление исходит только из theme, включая нулевые отступы и стандартные Material-значения. Компонент не подбирает собственные raw colors/размеры.

### Screens

Экран — детерминированная композиция DS, а не место бизнес-правил. Каждый экран в отдельной папке со своей темой компоновки и presentation-контрактом. Разрешены Flutter layout-примитивы (`Row`, `Column`, `Expanded`, slivers и т. п.), если их визуальные параметры получены из темы экрана. Новые кастомные визуальные элементы реализуются в DS, не внутри screen; private layout-fragment не служит обходом этого требования.

Экран получает controller/state через **presentation-контракт** и constructor injection. Контракт предоставляет типизированное отображаемое состояние/уведомления и действия; не раскрывает use cases, domain ports, инфраструктуру или глобальный контейнер. Данные отображения immutable. Экран наблюдает состояние и делегирует действия; не инициирует загрузку, navigation, вычисления или бизнес-переходы через lifecycle/build. Реальный controller выполняет сценарии через domain use cases по существующей архитектуре.

Независимость означает отсутствие ambient DI/router/live services, а не отсутствие аргументов. Preview-реализация контракта задаёт состояние без реальных use cases, сети и БД; её можно передать напрямую. При одинаковом contract snapshot, теме, locale, viewport и ресурсах экран имеет одинаковый визуальный результат.

Локальное состояние purely visual interaction возможно только когда это часть явного presentation-контракта/сценария: результат capture не зависит от случайного таймера, текущего времени или скрытого history. Анимация снимается в фиксированной фазе либо отключается для сравнения.

### Widgetbook

Widgetbook — preview-adapter внутри presentation. Он импортирует DS/screens и передаёт им темы/fixtures, но продуктовый UI не импортирует Widgetbook. Каждый use case живёт в своей папке соответствующего scope; регистрация отдельно от реализации UI. Сценарий не копирует component/screen и не содержит бизнес-логики.

Пустая оболочка каталога — tooling UI стороннего пакета, не новый проектный компонент DS; ей не создаётся ложный component golden. Entry point запускает тонкий `app` bootstrap; оболочка/каталог находятся в presentation. Временное standalone решение задачи 32 заменяется этой схемой.

## Перенос существующего кода

Исходный `main.dart` с Hello World — legacy-шаблон. Он не является новым компонентом и не признаётся соответствующим новой DS. При первой задаче основного UI шаблон удаляется/переносится в presentation с темой и локализацией. Новые widgets вне presentation не добавляются. Текущий scope задачи 33 переносит только оболочку Widgetbook; не имитирует полноценную миграцию приложения.

## Проверка и последствия

Каждый новый визуальный элемент получает тему, изолированный scenario и executable golden. Каждый screen открывается отдельно с preview-контрактом, минимум mobile/desktop. Новые визуальные параметры добавляются в foundation/тему до использования. Ссылки на UI-папки в правилах не заменяют проверку импортов и фактического потока данных.

Автоматический architecture checker сейчас проверяет границы слоёв по imports, а не все внутренние границы DS/screens/Widgetbook. Новые ограничения проверяются review; отдельный parser/checker не объявляется реализованным этой документацией.
