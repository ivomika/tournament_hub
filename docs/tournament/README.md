# Домен турнира

## Реализованные этапы

Tournament draft создаётся локально на одном устройстве из обязательного профиля владельца и гостей. Минимальный состав — два участника. Каждый участник сохраняется как самостоятельный snapshot с source `localProfile` или `guestProfile`; nickname исходного профиля не является живой ссылкой.

Поверх состава реализована подготовка стартового состояния турнира. Заменяемый `TournamentRules` формирует детерминированное расписание одного круга round robin, а независимый `FighterAssignmentStrategy` назначает участникам уникальных бойцов. Production-стратегия назначения использует управляемый источник случайных индексов, поэтому её можно воспроизводимо тестировать и заменять без изменения application-сценария.

Расписание представлено упорядоченной матрицей раундов. При чётном составе создаётся `N - 1` раундов без bye, при нечётном — `N` раундов с одним bye в каждом. Domain-модель расписания самостоятельно проверяет количество матчей, уникальность каждой пары, покрытие состава и запрет повторного участия игрока в одном раунде. `TournamentSetup` дополнительно проверяет полноту назначений и уникальность бойцов, не доверяя конкретным реализациям стратегий.

Подготовка сама не меняет статус draft. Отдельный application-сценарий старта создаёт `ActiveTournament` и сохраняет его до возврата успеха. Подключение этого сценария к UI входит в задачу проведения турнира.

## Экраны турнира

После успешного создания draft приложение подготавливает `TournamentSetup` и открывает экран обзора. Обзор показывает название, количество участников и раундов, а также snapshot каждого игрока с назначенным бойцом и локальным avatar. Presentation получает готовое расписание и назначения и не повторяет domain-расчёты.

Из обзора отдельным маршрутом открывается прокручиваемый экран раундов. Каждый раунд показывает все пары игроков; при нечётном составе явно указан участник с bye. Для каждого матча показаны текущий счёт, номер следующей схватки и два участника с nickname, avatar и именем бойца.

Host выбирает победителя каждой схватки отдельно. На время атомарного сохранения все кнопки ввода блокируются; ошибка не меняет показанный счёт и позволяет повторить выбор. После завершения доступно явное исправление итога на любой допустимый normal result.

На телефоне обзор использует одну колонку, на широком окне сводка и список участников располагаются рядом. В карточке матча участники располагаются в одну колонку на узком экране и рядом на широком.

## Проведение матча

Каждый запланированный матч имеет стабильный ID и собственную последовательность схваток best-of-three с нумерацией от 1. Победителем схватки может быть только участник матча; после второй победы автоматически формируется normal result `2:0`, `2:1`, `1:2` или `0:2`, и обычное добавление схваток блокируется.

Normal и technical results являются разными domain-типами даже при одинаковом счёте. Повтор одного update ID идемпотентен. Исправление завершённого результата выполняется отдельной командой: прежняя последовательность заменяется новой полной последовательностью, после чего все производные standings должны быть пересчитаны из авторитетной истории матчей.

## Хранение активного турнира

Drift schema v4 хранит marker активного турнира с ID и версией ruleset, назначения бойцов, раунды, матчи, схватки и применённые update ID. Расписание и результаты восстанавливаются в domain-модель с повторной проверкой инвариантов.

Запись полного согласованного состояния выполняется одной транзакцией. Application-сценарии запуска и изменения матча возвращают новое состояние только после успешного commit; при ошибке транзакция откатывается целиком.

Создание нового draft явно и в той же транзакции удаляет marker и дочерние данные прежнего текущего турнира перед записью нового состава. Repository не полагается на настройку SQLite `ON DELETE CASCADE`, поэтому старый active marker не может быть восстановлен вместе с новым draft.

При завершении active marker атомарно заменяется неизменяемым finished snapshot. Snapshot хранит применённые `rulesetId`/версию, все авторитетные матчи, итоговые строки и champion; повторное завершение по тому же tournament ID идемпотентно. После перезапуска UI читает сохранённый итог, а не пересчитывает его новой реализацией правил.

## Целевая модель MVP

MVP использует агрегат Tournament формата round robin: расписание по раундам, обычные и технические результаты, уникальное назначение бойцов, standings projection, этапы tie-break и неизменяемый итоговый snapshot.

Основные инварианты:

- Игрок не играет сам с собой.
- До изменения состава каждая основная пара встречается ровно один раз.
- Игрок участвует не более чем в одном основном матче раунда.
- Каждый активный игрок имеет одного бойца, бойцы не повторяются.
- Standings полностью воспроизводится из участников, матчей и результатов.
- Повторное применение одного результата не меняет итог второй раз.
- История завершённых матчей сохраняется при выходе игрока и позднем изменении состава.
- Завершённый турнир не содержит неразрешённых ничьих по местам.

## Очки, таблица и чемпион

Ruleset MVP имеет ID `mvp-round-robin` и версию `1`. Он выбирается до старта и не меняется внутри начатого турнира. Очки начисляются по схеме `2:0 → 3/0`, `2:1 → 2/1`, `1:2 → 1/2`, `0:2 → 0/3`; technical `2:0` участвует в таблице как обычный `2:0`.

Порядок ранжирования: очки, победы, разница схваток, выигранные схватки, личные встречи. Если остаётся равенство, завершение блокируется до Tie-Break Stage. Чемпион вычисляется только из единственного первого места после завершения всех матчей.

Scoring, tie-break и champion selection определены независимыми domain-интерфейсами. Альтернативный ruleset можно подставить через composition root без изменения матчей и UI.
