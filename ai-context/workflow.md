# Экспериментальный workflow разработки

Это канонический процесс постановки и реализации задач TournamentHUB. Указатели из AGENTS, README, rules и skills не дублируют его требования. Процесс применяется к обычным запросам «добавь feature» и «возьми задачу N» без обязательного вызова skill. Существующие правила архитектуры, типизации, тестирования и документации сохраняются.

## Режимы и состояние

- **CODE** — изменение кода приложения, tooling, скриптов или runtime-конфигурации. Нужны specification, plan и проверки по scope; TestGate требуется только для логики по классификации ниже.
- **DOCUMENTATION** — только текстовая документация, инструкции skills и метаданные. Нужны постановка, plan и структурные/сценарные проверки; искусственный RED не требуется.
- **PLANNING_ONLY** — явно запрошена только постановка, в том числе вызов skill task. Результат — зарегистрированная/уточнённая задача; тесты и реализация не начинаются без отдельного запроса. Такой запрос начинает CODE workflow, а не заменяет approval после тестового gate.
- Read-only вопросы и аудиты не начинают реализацию и не создают задачи только ради отчёта.

Если scope смешанный или при DOCUMENTATION появляется изменение кода, применяется CODE. Классификацию и причину записывай в карточку.

## Область TestGate

TestGate — test-first подтверждение RED (либо baseline GREEN для сохраняющего поведение refactor) и обязательная остановка для human approval перед реализацией. Это не синоним проверки качества любого изменения.

- **REQUIRED**: бизнес- и прикладная логика — domain, use cases, infrastructure adapters, хранение, сериализация, протоколы, app-оркестрация/DI/routing, state/controllers, вычисления и валидация. Для инструментов сюда относятся сбор и анализ фактов, контракты данных, правила checker. Определяет поведение, а не название папки.
- **NOT_REQUIRED**: чистое отображение — оформление, токены/темы, layout, визуальные компоненты, композиция экранов без изменения логики; отображение графа, zoom/pan/drag и другие визуальные взаимодействия без изменения предметных данных. Сюда же относятся конфигурация локального запуска/debug-профилей и документация.
- Если визуальная правка изменяет state machine, данные, расчёты, бизнес-действия или технический контракт, соответствующая часть требует gate. Нельзя обойти gate переносом логики в widget/viewer.
- В смешанной задаче выдели логическую часть и применяй gate к ней; независимую визуальную часть можно выполнять без ожидания gate логики. Не создавай новый номер только из-за этого разделения.
- В карточке укажи `TestGate: REQUIRED / NOT_REQUIRED` и краткую причину; при изменении scope пересмотри классификацию. Для read-only работы классификация не разрешает implementation.

Без TestGate после SPEC_READY → PLAN_READY разрешён переход в IMPLEMENTING по запросу пользователя, затем VERIFYING → DONE. Не нужны искусственный RED, тест наличия каждого параметра или дополнительное approval ради визуальной/конфигурационной правки. Проверки по риску, архитектурные ограничения, документация решений и честное evidence сохраняются; объём задаёт R-007. Качество не подтверждается отсутствием gate.

Для Flutter project UI обязательные goldens по R-006.c выполняются независимо от TestGate. Агент обновляет затронутые Linux baselines и показывает результат; это не требует RED/human approval визуальной части и не разрешает обход gate логики.

Task-list остаётся источником статуса; карточка — источником текущего этапа, specification, ответов, plan, evidence и approval. Поле Stage не создаёт новые статусы task-list.

| Статус | Применение |
| --- | --- |
| 🟣 | Только запланированная задача, включая PLANNING_ONLY |
| 🚧 | Выполнение, в том числе подготовка тестов и AWAITING_APPROVAL |
| 🔴 | Необходимое уточнение/внешнее препятствие, без которого нельзя продолжить |
| ✅ | Проверенные критерии и завершённая задача |

Исполнитель обновляет состояние и историю. Кодовая задача всегда имеет карточку; для простой документационной задачи сохраняется прежний выбор detail по сложности. Обратная связь продолжает исходный номер; независимая цель получает следующий номер из task-list. Перед изменениями реализации поставь 🚧. Для planning-only создание записи не означает начало реализации и сохраняет 🟣.

## Discovery и clarification

1. Прочитай context в порядке AGENTS: README, router, core, task-list/detail, применимые scope rules. Для новой цели найди связанные действующие документы, код и тесты. Прочитай этот workflow.
2. Для запроса «возьми задачу N» найди точный существующий номер; не изобретай формат TH-ID. Для «следующей задачи» выбери первую запланированную по порядку реестра. Если запланированных нет или выбор неоднозначен, сообщи об этом и уточни, не создавая цель самостоятельно.
3. Возобновляя работу, прочитай Stage и evidence карточки, текущий код и изменения. Не считай прежний статус 🚧 или старый approval разрешением на новый scope. Старая карточка без этапов дополняется при продолжении; закрытые карточки не переписываются массово.
4. Установи, какие ответы уже содержатся в действующих project/business rules и tests. Историческое описание задачи и сохранённый JSON не доказывают существование актуального поведения. Отсутствующую документацию не заменяй догадкой.
5. Покажи понимание цели и scope. Интерактивно задавай только нерешённые вопросы, по небольшим связанным группам. Не спрашивай заново то, что однозначно определено файлами.
6. Регистрируй цель/карточку в существующем ai-context; записывай полученные ответы в «Уточнения и решения» с датой и контекстом, сохраняя дословные prompts/ответы в Changelog. Не теряй ответ между чатом и spec.

Агент может предложить общее business rule и объяснить его влияние. Самостоятельно утверждать или добавлять обязательное бизнес-правило проекта нельзя. Task-specific решение также исходит из требований/ответов пользователя. Новый общий смысл становится каноническим только после явного подтверждения пользователя и документирования в docs. Если ответ противоречит действующему правилу, покажи конфликт и уточни, какое решение должно стать каноническим.

Нерешённый вопрос, влияющий на поведение/проверку, блокирует зависимую работу: Stage BLOCKED, статус 🔴, вопрос и предыдущий этап в карточке. Технические решения внутри утверждённых границ агент принимает самостоятельно и документирует существенные решения.

## Specification и plan

В карточке обязательны:

- Goal/Context: результат и основания в документах/коде;
- Scope/Non-goals: что входит и что не меняем;
- Уточнения и принятые task-specific решения;
- Наблюдаемые Acceptance Criteria с устойчивыми ID;
- Важные ошибки и крайние случаи;
- Test Scenarios, сопоставленные с критериями;
- Implementation Plan и version specification/plan/test set.

Dependencies и Architecture Impact добавляй по необходимости. При отсутствии пиши «нет» с кратким основанием, если это влияет на проверку. Business assumptions, влияющие на критерии, не оставляй скрытыми в plan.

Plan хранится в карточке, показывает ответственность компонентов, ожидаемые места изменений и проверки. Отмечай ограничения/нежелательные решения, относящиеся к задаче. Покажи пользователю краткий plan перед тестами. Отдельный approval на создание теста не требуется; production-код пока запрещён.

Этапы: DISCOVERY → SPEC_READY → PLAN_READY. Существенные изменения spec/plan/test set получают новую version и запись причины. Регистрационный номер задачи от этого не меняется.

## Тестовое подтверждение для CODE

Этот раздел и следующий human gate применяются только при `TestGate: REQUIRED`. При NOT_REQUIRED выбирай релевантные проверки без test-first остановки по разделу «Область TestGate» и R-007.

Сначала установи baseline релевантных существующих tests. Выбери объём регрессии по impact; обязательные scope-checks сохраняются. Запиши команды и почему выбраны именно они. Нет единого требования запускать весь проектный suite для каждой задачи, но выбранный обязательный набор должен оставаться проверяемым.

Для нового/изменённого поведения и bug fix:

1. Напиши/измени executable tests по согласованным критериям. Используй реальные бизнес-объекты/use cases; внешние БД/сеть допускают fakes или mocks. Не подменяй проверяемую бизнес-логику. Несколько критериев могут покрываться одним сквозным сценарием; покрытия важных ошибок/границ это не отменяет.
2. До approval меняй только тесты и явно тестовый harness/fixtures. Production API, заглушки, реализации и runtime-конфигурация не меняются ради компиляции теста. Если тестовая подготовка требует runtime-изменения, остановись и уточни ограничение.
3. Запусти тест и подтверди RED по ожидаемой причине. **Compile failure разрешён**, если диагностика соответствует отсутствующему capability/API из spec. Ошибка команды, отсутствие SDK/зависимости runner, не относящийся к сценарию syntax error и неожиданная причина не являются подтверждённым RED.
4. Запиши evidence: test paths/revision, команда и cwd, дата, exit/result, существенная диагностика, ожидаемая причина и связь с критериями. Сохрани сведения о baseline/regression и изменение набора тестов. Не записывай чувствительные данные логов.

После подтверждения: Stage RED_CONFIRMED → AWAITING_APPROVAL. Тест, который сразу GREEN, не доказывает новую feature: проверь, существовало ли поведение уже и нужен ли вообще production diff. Не создавай искусственный отказ ради этапа.

Для самостоятельного refactor/mechanical change **без смены поведения** действует утверждённое исключение: подтверждённый BASELINE_GREEN. Проверь покрытие сохраняемого поведения; при необходимости добавь characterization tests. Запиши, почему RED не нужен и что должно сохраниться. Затем Stage BASELINE_GREEN → AWAITING_APPROVAL; human gate обязателен и здесь.

Если необходимую проверку нельзя запустить, статус 🔴/BLOCKED с причиной и вопросом дальнейших действий. Нельзя выдавать отсутствие запуска за RED/GREEN. Прямые ограничения пользователя, включая запрет билдов, обязательны.

## Human gate и approval

В AWAITING_APPROVAL **остановись и закончи ход сообщением пользователю**. Кратко покажи цель, согласованный scope/критерии, plan и смысл тестового подтверждения: RED и его причина либо baseline GREEN с основанием исключения. Назови оставшиеся вопросы, если есть.

Diff тестов и команду не обязательно показывать в чате: evidence сохраняется в карточке и доступен для проверки. Нельзя просить одобрить RED, который не был реально запущен/подтверждён.

Для части с REQUIRED production implementation разрешена только после новой явной реплики пользователя, однозначно относящейся к этому gate. Контекстные «ок», «делай», «подтверждаю» подходят. Молчание, правильный plan/тест, исходный запрос feature, решение другого агента и реакция на другой вопрос approval не заменяют. Если адресат или версия согласования неясны — уточни. NOT_REQUIRED не требует отдельного согласования TestGate.

До первого production-изменения запиши approval в карточку: кто (пользователь; имя только если известно), дата, дословный текст, task ID, контекст и versions spec/plan/test set, test evidence. Approval процесса разработки не утверждает отдельные будущие features.

При новой карточке/сессии право продолжить проверяется по этому record и текущему scope. Содержательное изменение критериев, business meaning или утверждённого теста снимает прежнее разрешение для новой версии: уточнение → spec/plan/test → evidence → новый gate. Значимая техническая правка plan, меняющая scope или архитектурные обязательства, также требует повторного gate. Локальные технические исправления в прежних границах записываются в историю и не требуют повторного approval.

## Implementation, GREEN и refactor

После approval для REQUIRED либо после PLAN_READY для NOT_REQUIRED: Stage IMPLEMENTING, статус 🚧. Реализуй минимальное согласованное поведение. Не добавляй unrelated improvements и не расширяй scope. Для REQUIRED запускай affected tests регулярно; ошибки реализации можно исправлять до GREEN без нового approval, если смысл spec/test не изменён. Для NOT_REQUIRED выполняй выбранные проверки по риску и фиксируй результат без искусственных RED/GREEN этапов.

Не ослабляй ожидаемый результат теста ради прохождения. Механические правки теста допустимы при сохранении утверждённого смысла, с записью причины. Новый смысл теста проходит gate до новой реализации.

Новая бизнес-неоднозначность: IMPLEMENTING → BLOCKED, статус 🔴, остановка зависимой реализации. Запиши вопрос и уже проверенные факты. После ответа обнови spec/plan/tests и повтори evidence/gate для REQUIRED, если меняется смысл или scope. При NOT_REQUIRED пересмотри классификацию: появившаяся логика требует gate. Ответ, только подтверждающий уже утверждённый смысл, записывается и позволяет вернуться к прежнему approved этапу.

GREEN означает успех нового/сохраняющего поведение тестового набора и выбранной обязательной регрессии. Запиши фактические результаты. Для refactor в baseline-ветке весь согласованный набор остаётся GREEN.

После GREEN возможен behavior-preserving refactor в пределах scope без отдельного approval: Stage REFACTORING. Сохраняй тесты и бизнес-смысл. Если regression становится RED, исправь или отмени собственное изменение, сохранив чужую работу; не называй refactor завершённым до возврата GREEN. Намеренная смена поведения требует сначала нового spec/test/gate.

## Verification и DONE

Stage VERIFYING. Проверить:

- все Acceptance Criteria подтверждены;
- логика с REQUIRED имеет executable coverage и test evidence GREEN; для NOT_REQUIRED выполнены соразмерные проверки из plan;
- обязательная регрессия и scope-checks прошли, ограничения честно записаны;
- архитектурные границы и project rules соблюдены;
- нет unrelated изменений и unresolved вопросов;
- существенные решения и docs обновлены;
- карточка, Changelog, plan и результаты отражают фактическое состояние.

Затем агент самостоятельно ставит Stage DONE и ✅ в task-list/карточке, сообщает результат и пределы проверки. Отдельная финальная human-приёмка не требуется. Невыполненный обязательный критерий не отмечается успешным; при REQUIRED нельзя заявить DONE без обязательного GREEN, при NOT_REQUIRED — без выбранных обязательных проверок.

DOCUMENTATION проходит DISCOVERY → SPEC_READY → PLAN_READY → IMPLEMENTING → VERIFYING → DONE со структурными/сценарными проверками. PLANNING_ONLY заканчивается на подготовленной постановке без перехода к implementation. Ни один режим сам по себе не разрешает коммит, push или сборку: соответствующие инструкции пользователя сохраняются.

## Существующие задачи и удаление эксперимента

Не переоформляй закрытые задачи. При возобновлении code task без stage/approval добавь необходимые разделы в текущую карточку и пройди gate; прежний исторический ✅ не утверждает новый scope. Существующие номера, статусы и append-only история сохраняются.

Процесс инструкционный: он не является техническим запретом tool-вызовов. Проверка исполнения требует просмотра истории/evidence, а не наличия заголовков.

Для удаления эксперимента по отдельному запросу: удалить этот файл и прямые указатели на него из AGENTS, ai-context README, R-007, task/audit skills и docs; убрать специальные template-подсказки gate или вернуться к обычному template. Дополнительные поля старых карточек остаются историческими данными. Это не требует удаления задач, второго реестра или изменения архитектурных rules. R-007 с общими требованиями тестирования остаётся; нормативный порядок утверждённого изменения сохраняется в задаче.
