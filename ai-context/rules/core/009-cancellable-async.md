# R-009. Отменяемость асинхронных операций

## Применение

Обязательное core-правило для нового и изменяемого асинхронного кода любой технологии: async-функций, Future/Promise/Stream API, подписок, таймеров и фоновых задач. Отсутствие async в сигнатуре не исключает правило.

## Ограничения

- Каждая проектная асинхронная операция имеет владельца и отменяемый контракт: token/scope либо handle отмены. Вложенная функция наследует контекст отмены владельца; не теряет его и не создаёт detached работу без явного владельца.
- Отмена идемпотентна, выражена типизированным исходом, завершает проектные ожидания и освобождает ресурсы. Отказ, ошибка, пользовательское закрытие и lifecycle cancellation не смешиваются. Поздний результат не меняет уже завершённое состояние и не доставляется повторно.
- Отмена передаётся вложенным операциям и внешнему источнику, когда API это поддерживает. Если физическая остановка невозможна, адаптер документирует ограничение, завершает проектное ожидание, подавляет позднюю доставку и учитывает уже совершённые side effects. Нельзя выдавать прекращение ожидания за остановку работы или rollback.
- unawaited/fire-and-forget, проверка mounted/isDisposed, timeout и простая обёртка Future сами по себе не обеспечивают отменяемость. Нужны владелец, отмена, обработка ошибок и освобождение ресурсов.
- Cleanup отмены должен завершаться и освобождать ресурсы; рекурсивное требование отменять сам cleanup не вводится. Необратимый шаг имеет документированную точку commit и честный исход при отмене после неё.
- Тесты покрывают применимые сценарии: отмена до старта/во время ожидания, повторная отмена, поздний результат и cleanup. При изменении старого async API несоответствие правилу нельзя скрывать; фиксируется затронутый дефект и необходимые изменения.

## Проверка

Review контрактов/ownership и поведенческие тесты. AST-автоматизация отменяемости пока отсутствует: наличие token или async не доказывает корректность. Правило не выбирает пакет lifecycle и не объявляет весь старый код соответствующим.
