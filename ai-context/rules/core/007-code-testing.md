# R-007. Обязательное тестирование кода

## Применение

Обязательное core-правило для изменений кода приложений, инструментов и скриптов любой технологии, включая исправления и рефакторинг.

Область TestGate, порядок test-first, допустимого compile RED, baseline GREEN и human approval определяются только [каноническим workflow](../../workflow.md). Gate обязателен для логики, а не для каждого визуального изменения или debug-конфигурации.

## Ограничения

- До изменения определи затронутое поведение/инварианты и подходящие проверки; зафиксируй их в задаче.
- Новая/изменённая бизнес- и прикладная логика покрывается автоматическими тестами нормального, ошибочного и граничного сценария в применимой степени. Для дефекта логики нужен воспроизводящий регрессионный тест. Подтверждение до implementation и успех после фиксируются по workflow.
- Для чистого визуала, визуальных взаимодействий и локальных конфигураций запуска объём проверок выбирается по риску: analyzer/структурная проверка, ручной запуск, просмотр размеров/состояний, целевые существующие tests при необходимости. Новые unit/widget/golden-тесты не обязательны для каждой правки; не добавляй assertions наличия констант/параметров лишь ради gate. Если проверяемое поведение затрагивает логику, применяется предыдущий пункт независимо от расположения кода.
- Рефакторинг проверяется существующими тестами сохранения поведения. Для механического изменения без нового поведения не добавляй тест, повторяющий реализацию; выбери достаточные существующие или структурные проверки и обоснуй выбор.
- Тест проверяет наблюдаемый результат или контракт. Изолированные тесты дополняются интеграционными, когда результат зависит от взаимодействия компонентов.
- Перед завершением выполни релевантные тесты, статический анализ и обязательные архитектурные проверки по scope. Наличие тестового файла без запуска не подтверждает успех.
- В задаче укажи команды, фактические результаты, покрытие и ограничения. Для логики lint, build и ручной просмотр не заменяют поведенческое тестирование; для чистого визуала/конфигурации выбранных соразмерных проверок достаточно.
- Соблюдай прямые ограничения пользователя, включая запрет билдов. Невыполненные проверки помечай с причиной; не отмечай зависимый критерий пройденным и не объявляй полную проверенность результата.
- Для изменений только документации, skills и метаданных проверяются ссылки, формат, согласованность и релевантные workflow; runtime-тесты неизменённого продукта не требуются.

## Проверка

Сопоставить поведение с покрытием и фактическими запусками. Проверить регрессию, границы и честность статуса критериев. Отсутствие записи о запуске обозначается отдельно: оно само по себе не доказывает, что тест не запускался.

Выбор проверок и отчёт: [Тестирование кода](../../../docs/development/code-testing.md).
