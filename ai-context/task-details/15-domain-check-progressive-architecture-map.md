# Задача 15. Перестроить Domain architecture checker для многоуровневого чтения связей

## Статус

🚧 В работе · этап 1 реализован, ожидает приёмки

## Цель

Сделать Domain architecture checker читаемым от общего устройства к конкретным зависимостям: добавить воздух и иерархию узлов, обзор областей с drill-down, объединение межкластерных связей и явные типы связей.

## Контекст и границы

- Задача состоит из четырёх строго последовательных этапов. После завершения каждого этапа агент останавливается, показывает результат и ждёт явной приёмки пользователя перед следующим.
- Агент не создаёт git-коммиты. После принятия каждого этапа он сообщает готовую команду `git commit` и предлагаемый русский текст коммита; выполнение команды остаётся за пользователем.
- Входит: только `tools/domain-check`, его документация и task metadata.
- Не входит: изменение Domain-кода, Flutter-приложения, публичных Domain contracts, JSON-инвентаря как источника архитектурных фактов без отдельного решения, а также подключение стороннего graph-layout framework.
- Несвязанные изменения generated plugin registrants не изменяются и не включаются в предлагаемые команды коммита.

## Этапы и обязательные точки приёмки

### Этап 1. Воздух и визуальная иерархия узлов

- **Текущий этап.** Этапы 2–4 не начинаются до явной приёмки пользователя.
- [x] Увеличить расстояния между карточками и кластерами.
- [x] Ввести три визуальных размера: prominent для aggregates, standard для entities/ports/repositories/models/abstractions и compact для value objects/failures.
- [x] Сохранить ручной характер «Фокуса связей»: он выключен по умолчанию, стартовый объект не выбирается автоматически.
- [ ] **Стоп:** показать результат и проверки; дождаться приёмки.
- Предлагаемый commit после приёмки: `feat: добавить иерархию узлов в domain-check`.

### Этап 2. Обзор областей и drill-down

- Добавить режим обзора, где area clusters представлены как узлы, а межобластные связи агрегированы по паре областей.
- Добавить явный переход в детальную карту области и возврат в обзор без потери фильтров, где это применимо.
- **Стоп:** показать результат и проверки; дождаться приёмки.
- Предлагаемый commit после приёмки: `feat: добавить обзор областей domain-check`.

### Этап 3. Объединение межкластерных связей

- В детальном режиме объединять параллельные связи между одними и теми же area clusters в подписанную шину с количеством связей.
- При выборе объекта или шины раскрывать конкретные edges без сокрытия исходных фактов inventory.
- **Стоп:** показать результат и проверки; дождаться приёмки.
- Предлагаемый commit после приёмки: `feat: объединить межкластерные связи domain-check`.

### Этап 4. Типизация связей

- Ввести явно ограниченный набор семантических типов edge (например, `uses`, `creates`, `stores`, `implements`) только после аудита фактических labels inventory.
- Показать тип связей текстом, маркером и фильтром; цвет не является единственным носителем смысла.
- Зафиксировать, как поддерживать edge type вместе с inventory.
- **Стоп:** показать итог, проверки и предложенную команду коммита; дождаться финальной приёмки.
- Предлагаемый commit после приёмки: `feat: типизировать связи domain-check`.

## Критерии готовности

- [ ] После этапа 1 карта имеет заметно больше воздуха и иерархию размеров без пересечений карточек; focus не становится default state.
- [ ] После этапа 2 пользователь может начать с карты областей и перейти к деталям области.
- [ ] После этапа 3 массовые межкластерные связи читаются как агрегированные шины и раскрываются по запросу.
- [ ] После этапа 4 каждый edge имеет текстово доступный тип, а типизация не подменяет архитектурные факты догадками.
- [ ] Каждый этап прошёл свои static/HTTP проверки и отдельную пользовательскую приёмку до перехода к следующему.

## Открытые вопросы и блокеры

- Таксономия edge types будет определена только на этапе 4 после аудита текущего `domain-architecture.json`; до этого labels не интерпретируются как формальный тип.

## Ключевые решения

- Progressive disclosure — основной принцип карты: сначала areas, затем clusters, затем конкретные edges.
- «Фокус связей» остаётся явным действием пользователя; default state показывает полную карту без предвзятого стартового узла.
- По обратной связи на приёмке этапа 1 горизонтальный коридор между карточками увеличен сильнее вертикального; допустимая цена — более широкая карта с горизонтальной прокруткой.
- Коммиты выполняет пользователь. Агент на каждой точке приёмки предоставляет только готовую команду и сообщение.
