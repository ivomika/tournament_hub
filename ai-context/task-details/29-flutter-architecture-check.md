# Задача 29. Архитектурная проверка Flutter

## Статус

✅ Завершена

## Цель и границы

Правило абсолютных Dart-импортов и AST-проверка зависимостей app/domain/infrastructure/presentation. Проверяются lib и test; приложение не собирается. Проверка импортов не доказывает отсутствие бизнес-логики в widgets, service locator или вызовов use cases вне state.

## Применимые правила

- R-001/R-002 — отдельная ответственность checker, документирование ограничений.
- R-004 — типизированные слои и результаты проверки.
- R-003.a/R-003.c — матрица зависимостей и независимость domain.
- R-003.b/R-003.d/R-005/R-006.a/R-006.b прочитаны; UI и бизнес-сценарии в задаче не меняются.
- [R-003.e](../rules/flutter/003-e-package-imports.md) — создано до checker; запрещает относительные директивы и закрепляет область структурной проверки.
- Conditional rules отсутствуют.

## Решения

- Используется существующий analyzer tooling package; новых зависимостей приложения нет.
- Тесты — отдельный потребитель всех слоёв; runtime-код не может импортировать test.
- Проверка охватывает структурные imports, а не корректность bootstrap, бизнес-правил, методов state или SDK-типов в публичных сигнатурах.
- Domain allowlist пока допускает чистый Dart SDK и ни одного внешнего пакета; Equatable не считается разрешённым автоматически лишь по наличию в pubspec.

## Итог

Правило и архитектурный тест реализованы и проверены. Текущий минимальный клиент проходит проверку импортов; это не утверждение о соответствии всего его UI остальным правилам. Предыдущие изменения правил закоммичены отдельно; эта задача подготовлена отдельным коммитом. Пуш не выполнялся.
