# 113. Обязательное контекстное логирование

## Статус и этап

Stage DONE. Specification1 / plan1. [Workflow](../workflow.md).

## Цель и scope

Закрепить обязательное диагностическое логирование, особенно критических фаз. По отказу должно быть понятно, какое действие и на каком этапе не завершилось, почему, с каким контекстом и последствиями. Одиночных общих фраз «Ошибка»/«Не удалось выполнить запрос» недостаточно.

Входит: самостоятельное core-правило R-010, обязательный router/registry, maintenance и docs с критериями/примерами достаточного лога. Не входит: аудит всего старого кода, массовое добавление событий, изменение Logger/вывода, автоматический анализ семантики сообщений, новые зависимости, сборки, запуск и коммит.

## Применимые правила

- Прочитаны обязательные core через [router](../rules/README.md): R-001 — не логировать каждую функцию ради формальности; R-002 — факты и пояснения в docs; R-004 — типизированные scope/event/reason; R-007 — структурная/сценарная проверка документации; R-008.a/b — понятность терминов и условий; R-009 — честная отмена, cleanup, владельцы async output.
- Прочитан [maintenance](../rules/maintenance.md): независимая ответственность получает следующий root R-010, без изменения прежних ID; router/registry/docs обновляются вместе.
- Scope rule — core для любой технологии. Flutter runtime/правила архитектуры Flutter не изменяются; конкретные существующие границы logger подтверждены [документом](../../docs/architecture/logging.md). Новое правило не разрешает обход слоёв или выдачу widgets инфраструктурных зависимостей.
- Conditional scan: других conditional rules нет. Новые локальные skills не нужны.
