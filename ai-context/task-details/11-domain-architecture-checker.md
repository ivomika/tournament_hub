# Задача 11. Создать Domain architecture checker

## Статус

✅ Выполнена

## Цель

Создать локальное Web mini app в `tools/domain-check`, которое визуализирует Domain-архитектуру TournamentHUB из машиночитаемого JSON-реестра.

## Контекст и границы

- Входит: JSON-инвентарь публичных Domain abstractions, интерактивный HTML/CSS/JS viewer, фильтры, поиск, карточка выбранного объекта и граф связей.
- Входит: Make-команда локального запуска и документация инструмента.
- Не входит: runtime-интеграция viewer в Flutter, автоматический Dart AST parser или редактирование Domain-кода через UI.

## Применимые правила

### Обязательные правила

- [x] [R-001 · SOLID](../rules/core/001-solid.md) — JSON отделяет данные архитектуры от viewer; HTML, CSS и JS имеют отдельные роли, а mini app не зависит от Flutter-кода runtime.
- [x] [R-002 · Документирование на русском](../rules/core/002-documentation-russian.md) — назначение, запуск и обязанность обновлять inventory вместе с Domain описаны в `tools/` и `docs/`.

## Открытые вопросы и блокеры

- Инвентарь поддерживается вручную в текущем инкременте. Автоматический AST parser будет отдельной задачей, если ручное обновление станет источником рассинхронизации.

## Ключевые решения

- JSON — единственный источник данных viewer. Он хранит сжатое архитектурное описание, а не копию исходного Dart-кода.
- Один node может объединять родственные простые value objects или failure subtypes, но каждый public Domain contract и бизнес-объект представлен в inventory.
