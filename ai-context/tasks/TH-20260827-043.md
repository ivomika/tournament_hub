# TH-20260827-043: Разделить rules и project facts, добавить design tokens и screen map

- Статус: Выполнена
- Создана: 2026-08-27
- Обновлена: 2026-08-27
- Источник: пользователь запросил рефакторинг rules, design tokens manifest, усиление документирования серьёзных решений и карту экранов.

## Цель

Сделать `docs` единственным владельцем продуктовых/архитектурных/дизайн-фактов, оставить в rules только исполняемые ограничения с ссылками на канон и дополнить канон machine-readable design tokens, screen map и policy серьёзных решений.

## Контекст

Аудит после задачи `042` подтвердил дублирование: domain lifecycle, breakpoints/tokens, MVP exclusions и data facts повторяются одновременно в rules и `docs`. Полная матрица всех 12 правил создаёт формальный шум. Нужна модель core rules + conditional rules, где facts живут только в `docs`, а rules определяют trigger, обязательство, запрет, каноническую ссылку и evidence.

## Границы задачи

### Входит

- Рефакторинг 12 rules без изменения продуктовой семантики.
- Core/conditional routing и новый task-card enforcement profile.
- Обновление `$task` под core evidence и conditional applicability.
- `docs/design/tokens.json` и документация его contract/usage.
- Каноническая карта экранов и переходов.
- Policy серьёзных решений, rule changes и architecture changes; журнал rule changes.
- Синхронизация `AGENTS.md`, AI-context, docs map, development guide и шаблона.

### Не входит

- Изменение lifecycle, tournament scoring, transport или application code.
- Реализация token generators/Flutter/Web themes.
- Закрытие существующих open decisions.
- Изменение `docs/source` и fighter assets.

## Требования и ограничения

- Project fact имеет одного владельца в `docs`; rules не копируют значения/списки/state machines.
- Core rules применяются всегда; conditional rule читается и применяется при совпадении trigger.
- Rule содержит только trigger, обязательно, запрещено, канон и evidence.
- Design manifest валиден JSON и является единственным владельцем числовых/цветовых design token values.
- Серьёзное решение нельзя оставить только в code/task/chat; architecture change требует ADR, rule change — отдельной записи rationale/impact/migration.

## Критерии приёмки

- [x] Rules не содержат дублирующих state machines, token values, breakpoint values и полный MVP exclusion list.
- [x] Core/conditional rules однозначно маршрутизируются и отражены в task template/skill.
- [x] Design tokens manifest валиден, документирован и связан из design rule/docs.
- [x] Screen map покрывает общую shell, Host, Participant, Spectator, guards и error/stale states.
- [x] Каждое серьёзное решение, architecture change и rule change имеет обязательный артефакт и traceability.
- [x] Structural/link/JSON/skill/source-integrity checks проходят с зафиксированным ограничением стандартного skill validator.

## Проверка

- PowerShell `ConvertFrom-Json`: manifest разобран, обязательные группы присутствуют, spacing scale монотонна.
- Structural scan: 12 rule files имеют только обязательные секции `Trigger/Обязательно/Запрещено/Канон/Evidence`.
- Duplicate-fact scan вне `docs/source` и `tokens.json`: raw colors/breakpoints/state-machine fragments не найдены.
- Relative Markdown link scan: битых внутренних ссылок не найдено.
- `git diff -- docs/source`: пусто; исходные материалы не изменены.
- `git diff --check`: ошибок whitespace нет; выведены только предупреждения Git о будущей нормализации LF/CRLF.
- Стандартный `quick_validate.py` для `$task` запущен, но окружение не содержит модуль `yaml`; вместо глобальной установки выполнена ручная проверка frontmatter, имени skill и обязательного routing contract.
- Builds/tests приложения не запускались: application code не менялся.

## Журнал решений
