# TH-20260827-046: Исправить архитектуру Flutter design system и screens

- Статус: Выполнена
- Создана: 2026-08-27
- Обновлена: 2026-08-27
- Источник: пользователь отклонил структуру задачи `045` и потребовал строгую theme-driven design system architecture с автоматическим architecture check.

## Цель

Перестроить Flutter presentation так, чтобы `presentation/design_system` владел generated tokens, общей темой и всеми UI-компонентами, каждый компонент находился в отдельной папке со своим `ThemeExtension`, а раздельные screen files только компоновали публичные design-system components; нарушения должны автоматически останавливать `make check`.

## Контекст

Текущая реализация хранит tokens вне presentation, объединяет компоненты и screens в крупные файлы, а компоненты напрямую читают generated tokens. Это создаёт неконтролируемую связанность и позволяет экранам обходить design system. Нужен исполняемый архитектурный контракт, а не договорённость в документации.

## Границы задачи

### Входит

- Перенос generated tokens и общей theme composition в `presentation/design_system`.
- Публичный barrel design system; screens не импортируют private tokens/themes.
- Отдельная папка и отдельный component theme для каждого visual component.
- Design-system primitives для текста, spacing/layout, actions, fields, navigation и surfaces.
- Разделение каждого screen preview в отдельный файл/папку; screens только компонуют DS API.
- Рефакторинг Widgetbook на новый публичный API.
- Dart architecture-check script и negative fixtures/tests для обязательной токенизации/границ.
- Подключение architecture check к `make check`.
- Усиление rule 06, architecture/design docs, ADR и rule-change log.

### Не входит

- Domain/application/network/persistence behavior и production router.
- Изменение значений canonical token manifest без обнаруженной необходимости.
- Visual redesign, лицензированные fighter assets или реализация React design system.

## Требования и ограничения

- Raw color/hex/Material `Colors.*` вне generated token output запрещены.
- DS component не импортирует generated tokens напрямую: только собственный `ThemeExtension` через `Theme.of(context)`.
- Component theme создаётся общей theme composition из generated semantic tokens.
- Screen не создаёт Material visual primitives напрямую и не импортирует component theme/tokens; допускаются только structural Flutter widgets и публичные DS components.
- Один component folder содержит widget, theme и при необходимости model; catch-all component files запрещены.
- Любое исключение architecture check должно быть точечным, документированным и связано с task ID.
