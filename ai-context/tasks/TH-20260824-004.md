# TH-20260824-004: Реализовать локальное хранение профиля и database client

- Статус: Выполнена
- Создана: 2026-08-24
- Обновлена: 2026-08-24
- Источник: запрос пользователя добавить database client для системы локальных профилей; уточнение — использовать Drift и Freezed с максимальной долей code generation.

## Цель

Обеспечить устойчивое локальное сохранение и восстановление профиля через database client и реализацию repository contract из `TH-20260824-003`.

## Контекст

Первый вход и редактирование профиля должны переживать перезапуск приложения. Domain не должен знать о выбранной database technology, схеме или DTO.

Зависимость: `TH-20260824-003` — domain-модель и repository contract должны быть определены до реализации адаптера хранения.

## Границы задачи

### Входит

- Подключение Drift, Freezed и необходимого code generation toolchain.
- Drift database client, инициализация, таблица локального профиля и версия схемы.
- Сгенерированные Drift rows/companions и Freezed data model/DTO.
- Преобразования между storage-моделями и domain с минимальным объёмом ручного mapping-кода.
- Реализация repository contract.
- Обработка отсутствующей записи и ошибок чтения/записи.
- Persistence tests, включая восстановление после повторной инициализации client.

### Не входит

- UI первого входа и профиля.
- Облачная синхронизация, backup и перенос профиля между устройствами.
- Хранение турнирной истории и других будущих таблиц, кроме общей безопасной подготовки database client к расширению.

## Требования и ограничения

- Local-first: создание или изменение профиля считается успешным только после устойчивой локальной записи.
- Изменение nickname не создаёт новый профиль и не меняет его identity.
- Data DTO и детали базы данных не проникают в domain.
- Повторная инициализация database client не должна терять сохранённый профиль.
- В качестве database technology используется Drift.
- Data model/DTO описывается через Freezed; сериализация и boilerplate генерируются там, где это применимо.
- Генерация выполняется через `build_runner` с генераторами Drift и Freezed. Generated-файлы запрещено редактировать вручную.
- Ручной код допускается только для domain boundary, бизнес-правил и преобразований, которые невозможно безопасно выразить генерацией.
- Схема должна с первой версии иметь явный `schemaVersion` и место для контролируемых migrations.
- Выбор executor/connection должен поддерживать целевые mobile и desktop платформы Flutter-приложения без зависимости domain-слоя от платформы.
- Политика хранения generated-файлов в Git должна быть явно зафиксирована при реализации и применяться единообразно.

## План

1. Подключить Drift, Freezed, `build_runner` и соответствующие генераторы, не добавляя ручной boilerplate.
2. Определить Drift-таблицу локального профиля, `schemaVersion` и базовую migration strategy.
3. Описать Freezed data model/DTO и сгенерировать необходимый mapping/serialization-код.
4. Реализовать lifecycle database client и минимальные явные преобразования на границе data/domain.
5. Реализовать domain repository contract поверх Drift client.
6. Добавить воспроизводимую команду code generation и проверку актуальности generated-кода.
7. Проверить round-trip, update, отсутствие записи, повторное открытие базы и выполнение генерации с чистого состояния.

## Критерии приёмки

- [x] Локальное хранение реализовано на Drift, data model/DTO — на Freezed.
- [x] Drift/Freezed boilerplate создаётся генераторами и не дублируется вручную.
- [x] Code generation воспроизводится одной документированной командой `build_runner`.
- [x] Generated-файлы не содержат ручных изменений.
- [x] Сохранённый профиль восстанавливается после повторного запуска storage layer.
- [x] Обновление nickname сохраняет identity и не создаёт дубликат.
- [x] Отсутствие профиля возвращается как нормальное состояние, а не неопределённая ошибка.
- [x] Storage-ошибки преобразуются в типизированные ошибки соответствующего слоя.
- [x] Persistence tests и статический анализ проходят.
- [x] Архитектурная документация или ADR описывает выбранное хранение.

## Проверка

- `make generate`: генерация Drift/Freezed успешно выполнена повторно без конфликтов.
- `flutter test test/features/profile/data test/features/profile/domain`: 9 тестов прошли, включая create/read/update/reopen round-trip.
- `flutter analyze`: проблем не обнаружено.
- Ручная проверка перезапуска приложения будет выполнена в интеграционной UI-задаче.

## Журнал решений

- 2026-08-24 — задача оставлена в статусе `Черновик`, потому что пользователь не определил конкретную database technology, а её выбор влияет на зависимости, платформы и миграции.
- 2026-08-24 — пользователь выбрал Drift для базы данных и Freezed для data models/mapping; задача переведена в статус `Готова`.
- 2026-08-24 — приоритет отдаётся code generation; ручной mapping сохраняется только на явной границе с domain, если полностью сгенерировать безопасное преобразование нельзя.
- 2026-08-24 — сгенерированные `.g.dart` и `.freezed.dart` хранятся в Git и никогда не редактируются вручную.
- 2026-08-24 — актуальный `build_runner` удалил параметр `--delete-conflicting-outputs`; воспроизводимая команда проекта — `dart run build_runner build`.

## Результат

Добавлены Drift `AppDatabase`, таблица локального профиля, Freezed DTO и `DriftLocalProfileRepository`. Хранилище поддерживает отсутствие профиля, атомарное сохранение единственного профиля, изменение nickname с прежней identity и восстановление после повторного открытия SQLite-файла. Команда `make generate` воспроизводит generated-код, который хранится в Git. Решение описано в ADR-0002.
