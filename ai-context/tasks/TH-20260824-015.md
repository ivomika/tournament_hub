# TH-20260824-015: Реализовать round robin сетку и назначение бойцов

- Статус: Выполнена
- Создана: 2026-08-24
- Обновлена: 2026-08-24
- Источник: запрос пользователя реализовать турнир «каждый с каждым», случайное назначение неповторяющихся персонажей и матрицу раундов через заменяемые domain-интерфейсы.

## Цель

Tournament Core формирует для валидного состава полное расписание одного круга round robin, сгруппированное по раундам, и назначает каждому участнику случайного уникального бойца через независимые заменяемые domain-стратегии.

## Контекст

В `TH-20260824-012` создан draft с immutable participant snapshots и предусмотрены точки подмены зависимостей. В `TH-20260824-010` реализован заменяемый `FighterRegistry` с полным roster MK11 Ultimate. Текущий Core ещё не создаёт матчи, раунды и назначения бойцов.

Подтверждённые правила проекта:

- формат MVP — один круг round robin;
- каждая пара участников играет ровно один основной матч;
- участник играет не более одного основного матча в раунде;
- при нечётном составе участник может получить bye;
- бойцы уникальны в активном турнире, назначаются случайно и блокируются после старта.

Зависимости:

- `TH-20260824-010` — registry бойцов и его domain-контракт;
- `TH-20260824-012` — Tournament Core, draft и participant snapshots.

## Границы задачи

### Входит

- Domain-модели раунда, запланированного матча и назначения бойца участнику.
- Абстрактный domain-интерфейс правил турнира, формирующий расписание из состава участников.
- Реализация правила одного круга round robin для чётного и нечётного состава.
- Представление расписания как упорядоченной матрицы раундов с матчами и явным bye там, где он необходим.
- Абстрактный domain-интерфейс стратегии назначения бойцов.
- Случайная выдача уникального бойца каждому участнику из переданного `FighterRegistry`.
- Управляемый источник случайности или эквивалентная точка подмены для детерминированных тестов.
- Application-сценарий подготовки турнира к старту, координирующий выбранные правила, назначение бойцов и проверку результата.
- Domain/application tests, включая property/invariant tests для диапазона размеров состава.
- Минимальная cross-platform корректировка существующей проверки fighter assets, необходимая для выполнения полного набора тестов в Windows.
- Актуализация архитектурной и турнирной документации, если итоговые контракты закрепляют устойчивое решение.

### Не входит

- Ввод и изменение результатов матчей, scoring, standings и tie-break.
- UI отображения матрицы раундов и назначенных бойцов.
- Изменение состава после старта, выход игрока и технические результаты.
- Сетевая синхронизация, Host/Participant/Spectator transport и persistence новых сущностей.
- Несколько кругов, play-off, швейцарская система и другие форматы турнира.
- Повторная выдача или ручной выбор бойца после старта.

## Требования и ограничения

- Domain-код остаётся чистым Dart и не зависит от Flutter, Drift, JSON, assets или платформенного random API напрямую.
- Конкретное правило round robin доступно через заменяемый domain-контракт; Tournament aggregate/application orchestration не должны зависеть от его реализации.
- Стратегия назначения бойцов является отдельным контрактом и заменяется независимо от турнирных правил.
- Для `N` участников создаётся ровно `N × (N - 1) / 2` основных матчей, каждая неупорядоченная пара встречается один раз.
- При чётном `N` создаётся `N - 1` раундов по `N / 2` матчей; при нечётном `N` — `N` раундов по `(N - 1) / 2` матчей и одному bye.
- В одном раунде участник встречается не более одного раза; при нечётном составе каждый участник получает ровно один bye за круг.
- Раунды и матчи имеют стабильный детерминированный порядок для одинакового входного состава; случайность применяется только к назначению бойцов.
- Один fighter ID назначается не более чем одному участнику активного турнира.
- Если доступных бойцов меньше числа участников, подготовка турнира завершается типизированной domain-ошибкой без частичного результата.
- Результат стратегии проверяется domain-инвариантами независимо от доверия к конкретной реализации стратегии.
- Назначение бойцов должно быть воспроизводимо в тестах через fake/seeded источник случайности, не фиксируя конкретный production-алгоритм перемешивания как публичный контракт.
- Entity и value object используют Equatable; один production-файл сохраняет одну основную ответственность согласно правилам репозитория.

## Критерии приёмки

- [x] Для любого поддерживаемого состава из двух и более участников расписание содержит ровно `N × (N - 1) / 2` матчей.
- [x] Каждая пара участников встречается ровно один раз, а участник не появляется дважды в одном раунде.
- [x] Чётный состав создаёт `N - 1` полных раундов без bye.
- [x] Нечётный состав создаёт `N` раундов, и каждый участник получает ровно один bye.
- [x] Каждый участник получает ровно одного бойца, и fighter ID не повторяются в активном турнире.
- [x] При нехватке бойцов возвращается типизированная ошибка без частично подготовленного турнира.
- [x] Правила турнира и стратегия назначения бойцов подменяются независимо без изменения application-сценария и domain-моделей результата.
- [x] Тесты воспроизводимо проверяют случайное назначение через управляемую зависимость.
- [x] Domain/application и property/invariant tests, эквивалентные проверки `make check` для текущего Windows-окружения и production build проходят; документация актуализирована.

## Проверка

- `flutter test`: 69 тестов прошли, включая новые domain/application tests.
- Invariant tests для составов от 2 до 20 участников: подтверждены число раундов и матчей, уникальность всех пар, отсутствие повторного участия в раунде и ровно один bye на участника при нечётном составе.
- Assignment tests с управляемой последовательностью индексов: подтверждены воспроизводимость, уникальные fighter ID, неизменяемый результат и `InsufficientFightersException` при нехватке уникальных бойцов.
- Application tests с fake `TournamentRules` и `FighterAssignmentStrategy`: подтверждена независимая подмена и отклонение некорректных назначений итоговой domain-моделью.
- `dart format --output=none --set-exit-if-changed lib test`: 91 файл, изменений форматирования нет.
- `flutter analyze`: проблем не обнаружено.
- `npm.cmd run lint`: успешно.

- `npx.cmd prettier --check . --end-of-line crlf`: все web-файлы соответствуют Prettier в текущем Windows checkout.

## Журнал решений

- 2026-08-24 — реализация начата после подтверждения пользователя; статус синхронизирован с реестром.
- 2026-08-24 — после первого полного запуска тестов в scope добавлена нормализация путей существующего fighter asset test: Windows возвращает `\\`, тогда как manifest использует `/`; продуктовые контракты и assets не меняются.
- 2026-08-24 — расписание и назначение бойцов объединены в одну задачу, поскольку вместе образуют проверяемое стартовое состояние турнира, но реализуются через два независимых domain-контракта.
- 2026-08-24 — под «матрицей раундов» принято упорядоченное расписание `раунд -> матчи + возможный bye`; визуальная табличная матрица остаётся вне задачи.
- 2026-08-24 — случайность ограничена назначением бойцов; расписание остаётся детерминированным для стабильного хранения, тестирования и последующей синхронизации.
- 2026-08-24 — точный алгоритм случайного перемешивания не становится публичным domain-правилом; контракт требует уникальность и возможность управляемой подмены.
- 2026-08-24 — расписание и назначения объединяются в immutable `TournamentSetup`, который повторно валидирует результаты подменяемых стратегий и не доверяет их корректности.
- 2026-08-24 — задача завершена после полного Flutter test, статического анализа, web lint/test/build и release APK build; особенности запуска Make и Prettier в Windows записаны в проверках.

## Результат

Добавлены domain-контракты `TournamentRules`, `FighterAssignmentStrategy` и `RandomIndexGenerator`, реализация одного круга `RoundRobinTournamentRules`, случайная стратегия уникального назначения бойцов и Dart-адаптер случайности. Расписание моделируется через immutable матчи, раунды и `TournamentSchedule` с полной проверкой round robin; `TournamentSetup` гарантирует одно уникальное назначение на каждого участника. Application-сценарий `PrepareTournament` координирует правила, стратегию и существующий `FighterRegistry` без зависимости от конкретных реализаций.

Добавлены invariant-тесты round robin для составов 2–20, тесты назначения и подмены контрактов. Существующий fighter asset test нормализует разделители путей для Windows. Архитектурная и турнирная документация актуализирована. Persistence стартового состояния, UI матрицы, ввод результатов, standings и tie-break намеренно остаются за границами задачи.
