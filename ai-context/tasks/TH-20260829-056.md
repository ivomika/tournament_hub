# TH-20260829-056: Закрепить responsive layout и иерархию действий

- Статус: Выполнена
- Создана: 2026-08-29
- Обновлена: 2026-08-29
- Источник: аудит Widgetbook; рекомендации по адаптивности и CTA

## Цель

Закрепить width-контракты и правила primary/secondary/destructive действий так, чтобы mobile, tablet и desktop меняли композицию, а не только размер.

## Границы задачи

### Входит

- Контракты 320–479, 480–959, 960–1279 и 1280+.
- Responsive split, trailing action rail на desktop и safe-area/sticky action bar на mobile.
- Ограничение: один dominant primary action на viewport.

### Не входит

- Изменение business actions и domain permissions.
- Новый shell/header (предшествует 055).

## Требования и ограничения

- Не использовать `Wrap` как универсальный layout для header/actions.
- Last CTA не должен перекрываться нижней навигацией.

## Проверка

- `make architecture` — успешно.

- `flutter test` — успешно, 62 теста.
- Widgetbook screen matrix расширена до 320/375/599/768/1024/1280 px; все previews строятся без overflow.

- Golden matrix обновлена для шести host/participant экранов; вручную сверены `host_running_mobile` и `host_open_desktop`.

## Журнал решений

- 2026-08-29 — breakpoint matrix вынесена отдельно, чтобы не прятать адаптивность в отдельных экранах.
- 2026-08-29 — задача активирована после завершения 055. Новый архитектурный boundary не создаётся: responsive action composition размещается как самостоятельный компонент существующей `presentation/design_system`.

## Результат

Добавлен публичный `ResponsiveActions` с отдельным typed theme contract: constructor требует единственную primary action, а secondary и destructive передаются раздельно. `AppShell` получил `pageActions`: на mobile они закрепляются в safe-area над нижней навигацией, на desktop образуют компактный trailing rail в header. У shell появился medium padding contract. На новый placement переведены ключевые этапы host flow и participant final, обновлены Widgetbook use case, adaptive tests и goldens.

Итоговый routing сверен с diff: изменения ограничены layout/action presentation boundary, не меняют business actions, permissions, navigation transitions или domain. Новый ADR не нужен, поскольку компонент находится внутри существующей design-system границы.
