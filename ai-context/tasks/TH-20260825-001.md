# TH-20260825-001: Исправить открытие нового активного турнира

- Статус: Выполнена
- Создана: 2026-08-25
- Обновлена: 2026-08-25
- Источник: сообщение пользователя «не удалось открыть активный турнир», хотя турнир создан заново.

## Цель

Новый турнир надёжно запускается на чистой и ранее использованной локальной базе, а при реальной ошибке UI показывает диагностически полезную причину без потери пользовательских данных.

## Контекст

После реализации schema v4 контроллер перед стартом читает finished snapshot, затем `StartTournament` читает active marker и сохраняет новое состояние. Сейчас любое исключение этих разных операций скрывается сообщением «Не удалось открыть активный турнир», поэтому по UI нельзя отличить несовместимое локальное состояние, ошибку миграции и ошибку записи.

## Границы задачи

### Входит

- Воспроизведение старта нового турнира на чистой базе и после существующего active/finished состояния.
- Определение и исправление причины ошибки.
- Нормализованное пользовательское сообщение и сохранение исходной причины для диагностики.
- Regression tests ответственного слоя.

### Не входит

- Изменение ruleset, scoring или турнирного расписания.
- Очистка пользовательской базы без доказанной необходимости и явного безопасного сценария.

## Требования и ограничения

- Ruleset начатого турнира остаётся неизменяемым.
- Исправление не должно удалять корректный active или finished snapshot.
- Новый турнир сохраняется до сообщения об успехе.

## План

1. Воспроизвести все ветви и получить исходное исключение вместо общего сообщения.
2. Исправить repository/application/controller на нижнем ответственном слое.
3. Добавить regression tests чистой базы и переходов между состояниями.
4. Выполнить анализатор, тесты и актуализировать карточку.

## Критерии приёмки

- [x] Новый турнир открывается на чистой базе.
- [x] Новый турнир открывается при наличии несвязанного прежнего состояния согласно local-first контракту.
- [x] Ошибка не маскируется неоднозначным сообщением.
- [x] Regression и полные Flutter-проверки проходят.

## Проверка

- Repository/controller test чистого старта.
- Test создания нового турнира после finished/active состояния.
- `flutter analyze` и `flutter test`.

Фактически 2026-08-25: `flutter analyze` — успешно; repository suite — 13/13; полный `flutter test` — 110/110; `git diff --check` — успешно.

## Журнал решений

- 2026-08-25 — карточка детализирована и последовательно переведена через `Готова` в `В работе`; сначала исследуется фактическое исключение, автоматическая очистка базы запрещена.
- 2026-08-25 — причина: сохранение нового draft полагалось на `ON DELETE CASCADE`; при оставшемся старом active marker repository совмещал его с новым draft и восстановление нарушало domain-инварианты.
- 2026-08-25 — переход на новый текущий турнир выполняет явную очистку дочерних таблиц в одной транзакции; при ошибке вся очистка откатывается. Задача завершена после regression и полного suite.
- 2026-08-25 — для восстановления уже повреждённой базы marker с другим tournament ID игнорируется; повторный старт самостоятельно заменяет его корректным состоянием.

## Результат

`DriftTournamentRepository` теперь явно очищает finished/active marker, матчи, раунды, назначения и прежний draft в корректном порядке внутри транзакции, не завися от SQLite foreign-key pragma. Marker с ID другого draft не передаётся mapper, поэтому кнопка повтора восстанавливает и уже возникшее неконсистентное состояние. Добавлены regression tests замены прежнего active tournament и устаревшего marker. Контроллер отдельно показывает сообщения storage/validation ошибок и записывает исходную причину в debug log; общий fallback оставлен только для неожиданных исключений.
