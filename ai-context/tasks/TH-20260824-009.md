# TH-20260824-009: Создать domain-модель гостевого профиля

- Статус: Выполнена
- Создана: 2026-08-24
- Обновлена: 2026-08-24
- Источник: запрос пользователя реализовать гостевой профиль для локального турнира на одном устройстве.

## Цель

Получить независимую domain-модель гостевого профиля и application-контракты, позволяющие добавлять временных гостей в создаваемый турнир без создания постоянного локального профиля.

## Контекст

На устройстве уже существует один постоянный `LocalProfile`. При создании локального турнира владелец устройства участвует вместе с гостями, для которых не требуется отдельная авторизация или постоянная личная история.

Связанные завершённые задачи: `TH-20260824-003` и `TH-20260824-008`.

## Границы задачи

### Входит

- `GuestProfile` с отдельной стабильной identity внутри draft/турнира и nickname.
- Value objects, validation exceptions и Equatable equality.
- Абстрактный контракт управления коллекцией гостей для application-слоя.
- Операции добавления, переименования и удаления гостя до создания турнира.
- Domain/application tests.

### Не входит

- Постоянная авторизация гостя и превращение гостя в `LocalProfile`.
- Облачное хранение, network identity и синхронизация между устройствами.
- UI добавления гостей — он входит в `TH-20260824-014`.
- Удаление участника после старта турнира.

## Требования и ограничения

- `GuestProfile` не наследует `LocalProfile` и не подменяет его: это разные domain concepts.
- Identity гостя не зависит от nickname и сохраняется в tournament snapshot.
- Никнейм после trim не может быть пустым; дополнительные правила длины и символов не придумываются.
- Источник ID передаётся через абстракцию, а не вызывается напрямую из domain.
- Разные гости различаются по ID; уникальность nickname в одном турнире запросом не определена и не должна неявно ограничиваться.
- Файлы и каталоги разделяются по ответственности согласно `AGENTS.md`.

## План

1. Определить entity, value objects и validation для гостевого профиля.
2. Описать абстракцию генерации identity и контракт управления гостями draft.
3. Реализовать application use cases добавления, переименования и удаления.
4. Покрыть identity, validation и операции коллекции тестами.
5. Обновить domain-документацию при фиксации итоговых решений.

## Критерии приёмки

- [x] Гость создаётся с независимыми ID и nickname.
- [x] Переименование не меняет identity.
- [x] Пустой nickname отклоняется domain-слоем.
- [x] Гостя можно добавить, переименовать и удалить до создания турнира.
- [x] Domain/application API не зависит от Flutter, Drift или конкретного ID generator.
- [x] Тесты и `make check` проходят.

## Проверка

- Domain tests: создание, equality, rename и validation.
- Application tests с fake ID generator: add/update/remove и отсутствие связи с постоянным профилем.
- `flutter analyze` и `make check`: ожидается успешное выполнение.

## Журнал решений

- 2026-08-24 — гостевой и локальный профили моделируются разными entities, чтобы временный guest lifecycle не проникал в постоянный личный профиль.
- 2026-08-24 — duplicate nickname пока разрешены и различаются ID, поскольку правило уникальности не определено пользователем.
- 2026-08-24 — реализация начата; collection port остаётся синхронным и хранит только состояние текущей формы, устойчивым состоянием становится participant snapshot турнира.

## Результат

Добавлены чистая Equatable-модель `GuestProfile`, value objects и validation, общий port `IdGenerator`, заменяемая `GuestProfileCollection`, in-memory adapter и application-сервис управления гостями. Domain и application tests подтверждают независимую identity, rename, удаление, duplicate nickname и ошибки валидации. `make check` завершён успешно 2026-08-24.
