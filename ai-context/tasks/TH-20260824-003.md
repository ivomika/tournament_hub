# TH-20260824-003: Создать domain-модель локального профиля и контракт репозитория

- Статус: Выполнена
- Создана: 2026-08-24
- Обновлена: 2026-08-24
- Источник: запрос пользователя проработать систему локальных профилей с domain-сущностью и абстрактным репозиторием.

## Цель

Получить независимую от Flutter и способа хранения domain-модель локального профиля с nickname и абстрактный контракт для создания, чтения и изменения профиля.

## Контекст

Локальный профиль нужен для первого входа в приложение и последующего редактирования nickname. UI и database-реализация должны зависеть от domain-контракта, а не друг от друга.

## Границы задачи

### Входит

- Domain-сущность локального профиля.
- Необходимые value objects или типы идентификации профиля.
- Domain-правила создания и изменения nickname.
- Абстрактный repository contract без зависимости от базы данных и Flutter.
- Domain-тесты сущности и контракта поведения.

### Не входит

- Конкретная база данных и сериализация.
- Flutter-экраны и маршрутизация.
- Облачная учётная запись, пароль, токены и сетевая авторизация.
- Несколько профилей на одном устройстве, пока такое требование не будет подтверждено отдельно.

## Требования и ограничения

- Domain-код остаётся чистым Dart и не импортирует Flutter, database package или DTO.
- Профиль хранит nickname и стабильную identity, не зависящую от изменения nickname.
- Минимальная безопасная валидация: nickname после удаления внешних пробелов не может быть пустым.
- Ограничение длины и допустимые символы не определены запросом и не должны жёстко фиксироваться без продуктового решения.
- Repository contract должен позволять отличить отсутствие локального профиля от ошибки чтения.

## План

1. Определить domain-типы локального профиля, identity и nickname.
2. Зафиксировать операции создания и изменения nickname через domain API.
3. Описать абстрактный repository contract для загрузки и сохранения локального профиля.
4. Покрыть валидное создание, изменение nickname, сохранение identity и ошибки валидации domain-тестами.

## Критерии приёмки

- [x] Профиль можно создать с валидным nickname и стабильной identity.
- [x] Изменение nickname не меняет identity профиля.
- [x] Пустой после trim nickname отклоняется domain-слоем.
- [x] Repository contract не зависит от способа хранения и UI.
- [x] Domain-тесты проходят.
- [x] Связанная архитектурная документация актуализирована при появлении новых решений.

## Проверка

- `flutter test test/features/profile/domain`: 4 domain-теста прошли.
- `flutter analyze`: проблем не обнаружено; domain-модуль не зависит от presentation/data.

## Журнал решений

- 2026-08-24 — допущение для MVP: на устройстве используется один локальный профиль; поддержка нескольких профилей не добавляется без отдельного требования.
- 2026-08-24 — минимальная проверка nickname ограничена trim и запретом пустого значения, чтобы не придумывать неподтверждённые правила длины и символов.

## Результат

Добавлены `LocalProfile`, `LocalProfileId`, `Nickname`, типизированная validation exception и абстрактный `LocalProfileRepository`. Изменение nickname создаёт обновлённую immutable-сущность и сохраняет identity. В архитектурной документации зафиксирован один локальный профиль для MVP и нормальное состояние его отсутствия при первом запуске.
