# TH-20260824-012: Создать основу Tournament Core

- Статус: Выполнена
- Создана: 2026-08-24
- Обновлена: 2026-08-24
- Источник: запрос пользователя начать Tournament Core для турнира из локального профиля и гостей, минимум два игрока, на одном устройстве.

## Цель

Получить чистый Tournament Core, который создаёт валидный локальный tournament draft из обязательного владельца `LocalProfile` и гостей, формируя независимые participant snapshots и запрещая состав менее двух игроков.

## Контекст

Локальный профиль реализован в `TH-20260824-003`; гостевой профиль создаётся в `TH-20260824-009`. На первом этапе турнир полностью управляется на одном устройстве и не требует Host/Participant network session.

Зависимости:

- `TH-20260824-009` — guest profile domain.
- `TH-20260824-010` — fighter registry contract; реализацию Core можно начать с fake registry, но финальная интеграция требует завершения roster.

## Границы задачи

### Входит

- Tournament ID, name, status `draft` и immutable participant snapshots.
- Различение источника участника: local profile или guest profile.
- Application use case создания draft с обязательным текущим `LocalProfile`.
- Domain invariant: минимум два участника, то есть local profile и хотя бы один guest.
- Контракты `TournamentRepository`, ID generator и зависимых стратегий/registries.
- Типизированные validation errors и domain/application tests.

### Не входит

- Раунды, матчи, scoring, standings, tie-break и завершение турнира.
- Сетевая группа, подключение других устройств и Host authority.
- Конкретная Drift-реализация repository — `TH-20260824-013`.
- Экран создания — `TH-20260824-014`.
- Неподтверждённое правило назначения бойцов.

## Требования и ограничения

- Tournament Core — чистый Dart без Flutter, Drift, asset API и platform imports.
- Участник хранится как snapshot; последующее изменение локального/гостевого профиля не переписывает уже созданный draft автоматически.
- Local profile включается обязательно и не может быть добавлен дважды.
- Draft с количеством участников меньше двух отклоняется domain-слоем.
- Зависимости от ID, времени, registry, назначения бойцов и persistence выражаются узкими ports и передаются снаружи.
- Не создавать abstraction без точки подмены; каждый port должен иметь fake для tests и минимум одну ожидаемую adapter implementation.
- Value equality через Equatable, data models через Freezed, один основной public type/ответственность на файл.

## План

1. Определить минимальные entities/value objects/status и participant snapshot.
2. Зафиксировать domain factory/aggregate invariants создания draft.
3. Описать узкие ports для ID, repository и опциональных стратегий.
4. Реализовать application use case из local profile и guest collection.
5. Покрыть minimum participants, local-owner uniqueness, snapshots и заменяемые dependencies тестами.
6. Обновить архитектурную и tournament-документацию.

## Критерии приёмки

- [x] Draft создаётся из одного local profile и одного или нескольких guests.
- [x] Состав менее двух игроков отклоняется domain validation.
- [x] Local profile присутствует ровно один раз.
- [x] Participants являются snapshots и различают local/guest source.
- [x] Core не зависит от UI, Drift, asset implementation и сети.
- [x] Все точки подмены имеют contract tests/fakes и не требуют изменения Core.
- [x] Domain/application tests и `make check` проходят.

## Проверка

- Domain tests: 1 участник отклоняется; 2+ принимаются; local owner не дублируется.
- Snapshot test: изменение исходного nickname не изменяет созданного participant.
- Contract/fake tests: замена ID generator и repository не меняет use case.
- `flutter analyze` и `make check`: ожидается успешное выполнение.

## Журнал решений

- 2026-08-24 — первый Tournament Core ограничен draft creation и participant snapshots; матчевый engine выносится в последующие задачи.
- 2026-08-24 — local profile является обязательным владельцем/участником, так как пользователь описал состав как local profile + guests.
- 2026-08-24 — правило назначения бойцов не фиксируется до отдельного подтверждения, несмотря на добавление registry.
- 2026-08-24 — реализация начата; participant snapshot использует identity исходного профиля вместе с явным source, а отдельный generated ID нужен только агрегату tournament draft.

## Результат

Реализованы чистые Equatable entities/value objects `TournamentDraft` и `TournamentParticipant`, minimum/local-owner/duplicate invariants, snapshot factories, repository port и application use case `CreateTournamentDraft` с внедряемым `IdGenerator`. Fake repository и tests подтверждают validation, snapshot semantics и сохранение через port. Архитектурная и tournament-документация актуализированы. `make check` завершён успешно 2026-08-24.
