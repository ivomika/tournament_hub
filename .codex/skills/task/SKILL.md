# Task

Работать только с постоянной памятью задач проекта. Результат skill — обновлённые `ai-context/task-list.md` и детальные карточки в `ai-context/tasks/`, но не изменения приложения.

## Разрешённая область

Можно читать:

- пользовательский запрос текущего диалога;
- `AGENTS.md`;
- `ai-context/README.md`;
- `ai-context/task-list.md`;
- `ai-context/templates/task.md`;
- `ai-context/rules/README.md`, пять core rules и conditional rules, чьи triggers совпали со scope;
- существующие карточки `ai-context/tasks/*.md`.
- `docs/README.md`, `docs/product/open-decisions.md` и тематические документы, прямо необходимые для декомпозиции запроса.

Можно изменять только:

- `ai-context/task-list.md`;
- карточки в `ai-context/tasks/`.

Не изменять исходный код, тесты, `docs`, конфигурацию, шаблон задачи или другие файлы. Не запускать реализацию, сборку, миграции и внешние действия. Если вместе с `$task` пользователь просит выполнить работу, сначала только оформить задачи и остановиться; реализация требует отдельного следующего запроса.

## Порядок работы

1. Прочитать `AGENTS.md`, AI-context, rule router и пять core rules; затем проверить, нет ли уже совпадающих или связанных задач.
2. Через `docs/README.md` найти канонические требования и проверить open decisions для затронутой области.
3. Выделить из запроса цель, ожидаемые результаты, ограничения, зависимости, неизвестные данные и критерии завершения.
4. Разделить запрос на задачи по самостоятельно проверяемым результатам. Не превращать каждый технический шаг в отдельную задачу. Разделять работу, если части имеют разные результаты, зависимости, области ответственности или могут выполняться независимо.
5. Расположить задачи в порядке зависимостей. В каждой зависимой карточке явно указать ID предшествующей задачи.
6. Назначить следующий неиспользованный сквозной `NNN` после максимального номера в истории реестра и использовать его в имени карточки `TH-ГГГГММДД-NNN`. Номер не переиспользовать после удаления или завершения.
7. Создать для каждой новой задачи полную карточку по `ai-context/templates/task.md`. Сохранять намерение пользователя и не добавлять функциональность, которой он не просил.
8. Сопоставить scope с conditional triggers, прочитать все сработавшие rules и отразить их влияние в scope, plan, criteria, checks или ограничениях. Заполнить evidence пяти core rules и только сработавших conditional rules.
9. Ставить статус `Готова`, только если контекст достаточен, routing завершён и сработавшее правило не заблокировано open decision. При существенной неоднозначности ставить `Черновик`, фиксировать неизвестные данные и условие готовности; не придумывать продуктовые решения.
10. Добавить или актуализировать записи в разделе активных задач `ai-context/task-list.md`. Использовать плоский списочный формат из `ai-context/README.md`: emoji-статус, отдельный сквозной номер `NNN`, название и ссылка на полную карточку. Markdown-таблицы, группировку по датам и полный ID в видимой части строки не использовать. Существующие совпадающие задачи обновлять вместо создания дубликатов, сохраняя их номер, историю и принятые решения.
11. Проверить уникальность сквозных номеров, название, соответствие emoji словесному статусу, работоспособность ссылок, core evidence и полноту conditional routing.
12. Кратко сообщить пользователю, какие задачи созданы или обновлены, какие правила применимы, зависимости и открытые вопросы зафиксированы. После этого остановиться.

## Требования к карточкам

- Писать на русском языке, кроме технических идентификаторов и устоявшихся терминов.
- В `task-list.md` обозначать статусы только emoji: 📝 `Черновик`, 🟢 `Готова`, 🚧 `В работе`, ⛔ `Заблокирована`, ✅ `Выполнена`, 🚫 `Отменена`.
- Заполнять каждый раздел шаблона. Для неприменимого раздела явно указывать причину.
- Указывать дату routing, ссылку на router, evidence пяти core rules и результат conditional trigger scan.
- Добавлять прямую ссылку и evidence для каждого сработавшего conditional rule; не создавать декоративные строки для несработавших rules.
- При обновлении существующей задачи повторять routing, если изменился scope.
- Формулировать цель как проверяемый результат, а не процесс.
- В границах отдельно фиксировать, что входит и не входит в задачу.
- План описывать на уровне значимых этапов, не привязывая будущего исполнителя к неподтверждённой реализации.
- Критерии приёмки делать наблюдаемыми и проверяемыми.
- В разделе проверки указывать предполагаемые команды или ручные сценарии; фактический результат заполняется исполнителем позже.
- В журнале решений фиксировать только решения, принятые во время декомпозиции, и явно помечать допущения.
- Не записывать пароли, токены, персональные данные и другие секреты.
