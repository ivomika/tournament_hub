# Аудит кода по правилам проекта

Работай в репозитории TournamentHUB. Аудит — read-only: не исправляй код или правила, не создавай задачи и коммиты только ради отчёта. Если пользователь отдельно просит исправления, оформляй их по процессу проекта.

## Актуальные правила

При каждом запуске заново прочитай `ai-context/README.md`, `ai-context/rules/README.md`, обязательные core rules из router, `ai-context/task-list.md` и связанную карточку. Затем прочитай обязательные flutter rules для Flutter scope и применимые conditional rules и документы, на которые выбранные правила опираются. Выполняй порядок чтения AGENTS.md; не используй запомненный список правил вместо файлов.

Сначала проверь правила на противоречия между собой и с канонической архитектурой, неоднозначность scope/исключений, недоступные ссылки и проверяемость ограничений. Не заменяй требования личными предпочтениями. Если правило неоднозначно, отдельно опиши проблему правила и не выдавай зависимое от трактовки подозрение за доказанное нарушение кода.

## Scope

Сверь router с `ai-context/rules/registry.json`: отчёт использует текущие leaf ID, например `R-003.d` и `R-006.b`. Registry содержит действующие группы, ID и пути. Core применяется ко всему коду; R-003/R-005/R-006 — только к Flutter-клиенту и его тестам, не к spectator/JS-инструментам. При аудите изменений правил прочитай `ai-context/rules/maintenance.md`, проверь scope, регистрацию, задачу и docs; выполни `node tools/check_rules.cjs`.

Определи scope из запроса; без указания используй `diff`.

- **diff:** `git status --short`, `git diff` и `git diff --cached`; добавь содержимое untracked-файлов из `git ls-files --others --exclude-standard`. Проверяется совокупное текущее изменение относительно HEAD; если HEAD отсутствует, staged-файлы рассматриваются как добавленные. Явно заданный пользователем base/ref имеет приоритет. Читай окружающий код и зависимости для проверки, но отделяй существующие проблемы вне изменения. Пустой diff означает отсутствие изменений для проверки, а не подтверждение качества всего проекта.
- **all / весь код:** составь перечень исходников приложений, tools, scripts, tests и конфигурации из Git и актуальных untracked-файлов. Исключи зависимости и build/cache-артефакты. Генерируемые файлы отметь отдельно: проверяй source/generator и актуальность результата, не предлагай ручное исправление generated-файла. Дроби проверку на группы; не объявляй проверенным код, который не прочитан. Указывай фактическое покрытие и ограничения.
- **task N / задача N:** найди точную строку N в task-list, прочитай detail/changelog, критерии и зафиксированные файлы/коммиты. Используй подтверждённый набор изменений: записанные refs, коммиты, paths и их актуальное содержимое. Не приписывай задаче весь текущий diff и не считай тему задачи доказательством принадлежности файла. Если карточка определяет только paths, проверяй эти файлы целиком и обозначай scope как файловый, без утверждения о происхождении каждой строки. Если набора файлов/коммитов нет, сообщи, чего не хватает для определения scope, проверь подтверждённую часть и запроси недостающие paths/ref. Не переключайся молча на all или diff.

После определения scope кратко назови его пользователю. Для каждой группы кода установи применимость правил: ограничения Flutter widgets нельзя автоматически переносить на JS-инструменты или data-классы. Неоднозначный scope других правил фиксируй в аудите правил.

## Проверка кода

Проверяй выбранные файлы по всем применимым rules. Используй `rg` для кандидатов, затем прочитай код и проследи импорт/значение/callback до источника. Совпадение regex само по себе не finding. Проверь контракты, места вызова use cases, типизированные ветвления, источники UI-текста и параметров оформления, назначение Widget-returning функций и анонимных callbacks.

Для каждого правила отметь: подтверждённые нарушения, проверено без findings, неприменимо с причиной или не проверено с причиной. Обоснованные исключения не считаются нарушениями. При diff отличай внесённую/усиленную проблему от существующей; существующие проблемы вне diff перечисляй отдельно и только если важны для понимания результата.

Используй существующие read-only проверки, если они помогают подтвердить finding. Соблюдай пользовательский запрет билдов; не запускай команды, которые переписывают source/generated-файлы, не устанавливай пакеты ради аудита. Отсутствие автоматической проверки не мешает ручному review, но ограничение покрытия должно быть явным.

## Отчёт

Сначала покажи подтверждённые findings по важности: `[P1/P2/P3] R-NNN · проблема`, абсолютный путь и точная строка, доказательство нарушения, последствие и направление исправления. P1 — существенный риск корректности/границ, P2 — обычное нарушение обязательного правила, P3 — локальная проблема низкого влияния. Приоритет определяется последствиями, а не только обязательностью правила. Объединяй повторения одной причины и указывай остальные места.

Отдельно перечисли проблемы самих правил, вопросы/неподтверждённые подозрения и покрытие: scope, baseline, просмотренные файлы, матрица применимости rules, выполненные проверки и пробелы. При отсутствии findings сообщи об этом только в пределах реально проверенного scope. Результат — аудит, а не сертификация всего проекта.
